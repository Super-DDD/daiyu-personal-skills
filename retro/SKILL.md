# retro

用户要求做一次**复盘**。目标是提出如何改进编码 agent 的**工作环境**，让以后做得更好。

## 步骤

1. 读取并使用 [`writing-for-agents`](../writing-for-agents/SKILL.md) 作为写作指南。
2. 阅读用户指定会话的一手资料。这可能需要在本机查找会话日志。如果用户没有指定会话，就使用当前会话。
3. 从这些方面寻找可改进的事项。

   - **导航。** agent 找到正确文件的过程顺畅吗？文件之间是否有隐含依赖？加一条导航指引是否能缩短查找过程？当会话花了很长时间才找到某条信息时检查这一项。
   - **自动检查。** 有哪些检查能发现 agent 已经犯过的错误？例如 lint、类型检查、测试或文件系统检查。先看仓库自己的检查命令，包括 `package.json` 或构建工具里的 `lint`、`check` 脚本和 CI 工作流。若检查已存在但没有接入，或它在无声地失效，应记录这个发现，避免重新造一个。仓库没有任何检查防线，例如既没有 pre-commit hook，也没有运行 lint、类型检查或测试的 CI 任务，本身就是一项发现。没有 lint 检查意味着项目持续错过发现错误的机会。当 agent 犯了自动检查能发现的错，或仓库没有这类防线时检查这一项。
   - **编码标准。** 是否应给**reviewer agent** 增加一条规则？是否应删除或澄清现有规则？先判断是什么类型的问题。机械性违规，例如固定的语法形态、禁止的 API、导入格式或文件位置，一律交给确定性的检查。可以选择仓库自己的 linter 自定义规则、新的 pre-commit hook 或新的 CI 任务，取最低成本的做法。默认建立检查。`CODING_STANDARDS.md` 留给真正需要判断的事项，例如跨文件的一致性或是否符合周围的写法。当reviewer agent 没发现某个错误时检查这一项。
   - **全局 `AGENTS.md`。** 哪些指导应移到编码标准或自动检查中？当仓库或用户全局的 `AGENTS.md` 很长时检查这一项。
   - **工具开销。** agent 有没有成本很高、可以简化的工具调用？是否有自定义工具、CLI 或 MCP 工具极其浪费 token？当 agent 发起了昂贵的工具调用时检查这一项。
   - **无效指令。** 指导文件里是否有一些要求根本没改变 agent 的行为？当这些文件很长或难以维护时检查这一项。
   - **信息访问。** 有没有办法让 agent 更容易取得信息？例如把开发服务器日志分流保存，或提供第三方服务的只读访问。当 agent 无法获得关键证据时检查这一项。
4. 按严重程度向用户呈现这些建议。

## 参考

### 实现与审查

工作要经过实现和审查两个阶段。implementation agent 的上下文压力最大，要负责探索、编码和调试。

reviewer agent 的上下文压力最小。它拿到的是 diff，通常无需探索，也通常无需写代码或调试。

因此应由reviewer agent 执行编码标准。

### 文件

仓库中有几种可用的文件。

- `CLAUDE.md`、`AGENTS.md` 会进入在此仓库工作的 agent 的 context window。极少量地使用它们，通常用来放导航指引。
- `CODING_STANDARDS.md` 在审查阶段读取。如果超过 1,000 行，就用导航指引指向相应文档目录。
- **文档**是由其他文件指向的参考资料。创建资料前，先找有没有现成的。
- **Skill** 也可以用来承载文档。它的描述会进入 agent 的 context window。按 `writing-for-agents` 的建议来写。
