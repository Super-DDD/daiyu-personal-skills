# ADR 格式

译自 [`domain-modeling/ADR-FORMAT.md`](https://github.com/mattpocock/skills/blob/abeeaf9/skills/engineering/domain-modeling/ADR-FORMAT.md)。

ADR 放在 `docs/adr/`，按顺序编号，例如 `0001-slug.md`、`0002-slug.md`。等需要写第一份 ADR 再创建这个目录。

## 模板

```md
# {决策的简短标题}

{用一到三句话说明背景、决定了什么，以及为什么。}
```

这样就够了。一份 ADR 可以只有一段。重要的是记下做了什么决定，以及为什么这么定。

## 可选部分

只有确实有价值时才加入这些部分。大多数 ADR 用不上。

- **状态**元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）。以后重新讨论决定时有用。
- **考虑过的选项**。备选方案值得记住时再写。
- **后果**。需要指出不明显的后续影响时再写。

## 编号

查看 `docs/adr/` 里现有的最大编号，再加一。

## 什么时候提议写 ADR

必须同时满足以下三条。

1. **难以逆转。** 以后改主意的成本不可忽略。
2. **缺少背景就会让人意外。** 未来的读者看见代码会想「当初为什么这么做？」
3. **经过了实在的取舍。** 当时确实有多个选项，你为某些明确的原因选了其中一个。

容易逆转的决定以后可以直接改。显而易见的决定通常没人会追问理由。只有一个明显选项时，也没有值得记录的取舍。这几种情况都可以跳过 ADR。

### 符合条件的例子

- **架构形态。** 「我们采用 monorepo。」「写模型采用事件溯源，并投影到 Postgres。」
- **上下文之间的集成方式。** 「订购与账务通过领域事件交互。」这个选择排除了同步 HTTP。
- **具有锁定效应的技术选择。** 如数据库、消息总线、认证服务商或部署目标。只记录替换可能耗费一整个季度的选择。
- **边界和范围决策。** 「客户上下文拥有客户数据，其他上下文只按 ID 引用。」明确排除的做法也值得记录。
- **有意偏离常规做法。** 「因为 X，我们手写 SQL。」合理的读者通常会以为这里用了 ORM。记录这个理由，避免下一位工程师把有意为之的做法当成问题修掉。
- **代码里看不见的限制。** 「合规要求使我们无法使用 AWS。」「合作方 API 契约要求响应时间低于 200 毫秒。」
- **被否决且理由不明显的备选方案。** 如果曾为细微的理由放弃 GraphQL、选择 REST，把理由记下来，省得半年后有人再次提起。
