# Walking Through Code

从用户想弄清的问题出发，选一条可以从业务入口读到结果的源码路线。用户已有明确目标时直接沿用；有几条差异明显的路线时，简述各自能回答什么，请用户选一条。图、调用树和源码链接使用同一版本。

阅读 MR 时，先核对当前 MR 相对其目标分支的 diff，用一张总览图标出受影响的调用方、模块和数据结构，再从中选一条业务路线。后续沿用总览图里已交代清楚的职责。

## 沿同一个场景通读源码

1. **活动图**　从业务触发画到可观察的结果，标明哪些条件会改变结果。图下简要解释关键分支。
2. **类图**　把活动图中的业务角色对应到真实的类和接口，说明谁持有状态、谁作出判断、谁使用结果。源码按模块和函数组织时，直接画出相应的模块和函数。
3. **调用树（call tree）**　从入口函数开始，用缩进表示调用层级，同一层按该场景中的调用顺序排列。沿树追踪一两个影响结果的值，说明它们在哪里产生、写入，又由谁读取。重点展开决定结果的调用。线程交错或异步返回的先后关系影响理解时，再补时序图。

在每个函数行末加一条简短注释，说明它在当前场景中的作用。需要读者打开源码核对时，在函数名后、注释前加上编号。

```text
submit_job()                # 接收用户提交的任务
├── build_request()  [1]    # 从任务配置读取优先级，填入请求
└── enqueue()               # 将任务加入待调度队列
    └── persist_job()  [2]  # 将优先级写入任务记录
```

树下沿用相同的编号，将函数名链接到对应源码，并说明要核对什么。

- [1] `build_request()` — 看它从哪个配置项读取优先级，以及缺少该配置时取什么值。
- [2] `persist_job()` — 看它把请求里的优先级写入任务记录的哪个字段。

阅读 MR 时，在相应编号下对照 diff，说明改动前后的行为；发生职责迁移时，指出现在由谁负责。

当这条路线已经回答最初的问题，且关键判断都能通过源码链接核对，就用一两句概括从业务入口到结果的过程。用户追问某个函数时，在原树上展开对应节点。若 MR 中还有值得单独理解的改动，指出下一条路线能回答什么，由用户决定是否继续。
