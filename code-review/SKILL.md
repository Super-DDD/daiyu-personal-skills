# code-review

以用户提供的固定参照点和 `HEAD` 之间的差异为对象，从两个维度审查。

- **Standards**。代码是否遵守仓库中已经写明的编码规范？
- **Spec**。代码是否忠实实现了原始 issue 或 spec 中的要求？

两个维度分别交给**并行 subagent**审查，彼此不会干扰对方的上下文。最后由此 Skill 汇总发现。为每个 subagent 使用一个全新的 context window。

你应当已经知道项目使用的 issue tracker。如果没有，请让用户运行 [`$setup-matt-pocock-skills`](../setup-matt-pocock-skills/SKILL.md)。

## 流程

### 1. 确定固定参照点

使用用户指定的参照点，可以是提交 SHA、分支名、标签、`main` 或 `HEAD~5` 等。如果用户没有指定，就向他们确认。

审查未提交的本轮实现时，以开工时的基线和本轮改动为准。用 `git status --short` 识别范围，同时检查 staged、unstaged 和新增文件的内容，把相同范围交给两个 subagent。范围内只有工作树改动时也可审查。

审查已提交的分支时，确定并记录差异命令 `git diff <fixed-point>...HEAD`。三个点表示与 merge base 比较。用 `git log <fixed-point>..HEAD --oneline` 同时记下提交列表。

继续前，先用 `git rev-parse <fixed-point>` 确认参照点能解析，再确认选定范围内有变更。参照点无效或没有差异时，应在此步结束检查。

### 2. 找到 spec 来源

按以下顺序查找原始 spec。

1. 提交消息里的 issue 引用，如 `#123`、`Closes #45`、GitLab 的 `!67`。按 issue tracker 文档中的流程获取。
2. 用户作为参数给出的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能对应的 spec 文件。
4. 都找不到就问用户 spec 在哪里。如果用户说明没有 spec，Spec subagent 将跳过审查，并报告「没有可用的 spec」。

### 3. 找到规范来源

搜索仓库里所有说明代码应如何编写的文件。如果存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，必须纳入。

无论仓库自身有没有成文要求，规范维度都要参考下面的**code smell 基线**。这是一组固定的 Fowler code smell，来自《重构》第 3 章。适用以下两条规则。

- **以仓库规范为准。** 成文的仓库规范优先。如果该规范认可某个会被基线标出的做法，略过这条异味。
- **每条都需要判断。** 给每条异味注明它只是线索，例如「可能存在 Feature Envy」。工具已经执行的检查可以略过。

每条异味都说明如何识别和改进。逐项对照 diff。

- **Mysterious Name**。函数、变量或类型的名称无法告诉读者它做什么或保存什么。重新命名。如果想不到准确的名称，可能是设计本身不清楚。
- **Duplicated Code**。变更的不同区块或文件出现了相同的逻辑结构。提取共享逻辑，供两处调用。
- **Feature Envy**。一个方法使用另一个对象的数据比自己的还多。把这个方法移到它主要使用的数据所在对象上。
- **Data Clumps**。相同的一组字段或参数反复成组出现。将它们聚合成一个类型，传递这个类型。
- **Primitive Obsession**。基本类型或字符串代表了值得拥有独立类型的领域概念。给它一个小类型。
- **Repeated Switches**。针对同一类型的相同 `switch` 或一连串 `if` 出现在多处。用多态替代，或让两处共享同一份映射。
- **Shotgun Surgery**。一个逻辑变更迫使 diff 在多个文件中零散修改。将总是一起改动的内容归到同一模块。
- **Divergent Change**。同一文件或模块因为多个互不相关的理由而被改动。拆开，让每个模块只有一个变更理由。
- **Speculative Generality**。为 spec 当前用不到的需求添加抽象、参数或钩子。删掉这些预留项并内联回去，等实际需求出现。
- **Message Chains**。调用方得依赖长串的 `a.b().c().d()` 来访问数据。让第一个对象提供一个方法，把这段访问路径藏在方法内。
- **Middle Man**。类或函数基本只负责转发。去掉中间层，直接调用真正处理工作的目标。
- **Refused Bequest**。子类或实现类忽略或覆写了大部分继承而来的内容。去掉继承，改用组合。

### 4. 并行启动两个 subagent

在前台同时发出两个 subagent 调用，然后汇总它们返回的报告。

**Standards subagent 的提示**应包括以下内容。

- 完整的差异命令和提交列表。
- 第 3 步找到的所有规范来源文件。另附上第 3 步的完整异味基线，因为 subagent 无法从别处取得。
- 任务简报。「按相关文件或 diff 区块报告：① diff 违反成文规范的每一处，注明规则所在文件及规则。② 发现的每条基线异味，写出名称并引用相关 diff 区块。区分硬性违规和判断事项。违反成文规范可以是硬性违规，基线异味一律需要判断，成文的仓库规范优先于基线。略过工具已经执行的检查。少于 400 词。」

**Spec subagent 的提示**应包括以下内容。

- 差异命令和提交列表。
- spec 路径或已取得的 spec 正文。
- 任务简报。「报告：① spec 要求但缺失或只实现了一部分的事项。② diff 中超出要求的行为，即范围蔓延。③ 表面已经实现，但实现疑似有误的要求。每条发现都引用 spec 对应的原句。少于 400 词。」

如果没有 spec，就跳过 Spec subagent，并在最终报告中说明。

### 5. 汇总

在 `## Standards` 和 `## Spec` 标题下并列呈现两份报告，可以原样保留或稍作整理。保持两个维度各自的发现和排序。

最后用一行总结，给出两个维度各自的发现总数及各自最严重的问题（如有）。维度之间保持独立，避免选出跨维度的「最严重问题」。

## 为什么要分两个维度

一项改动在两个维度上的结论可以不同。

- 代码遵守所有规范，却实现了错误的行为。规范通过，spec 未通过。
- 代码满足 spec 的全部要求，却违反了项目约定。spec 通过，规范未通过。

分开检查可以避免一个维度的结果掩盖另一个。
