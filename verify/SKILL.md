# verify

只说 `$verify` 时，检查最近一轮成果。指定对象或问题时，按指定范围检查。例如“检查这份学习笔记的概念是否一致”，就从笔记里的定义、例子和练习入手。

## 验证什么

先找出这次约定的目标和完成条件。阶段成果已可检查、关键假设缺少支持、结果偏离预期、刚完成修正或准备交付时，按当前问题和风险选择适用的判断依据。

- **Spec 是否满足** — 实际成果满足哪些目标、范围、约束和交付要求？把已经核实并纳入本次约定的项目要求一起对照。
- **概念完整性（Brooks，《人月神话》）** — 各部分能否用同一套设计思想和概念模型解释？沿一个具体用例检查职责、规则、接口和使用方式是否协调。读文档时也可以追踪同一术语，看定义和例子能否推出同一个结论。
- **复杂性（Ousterhout，《软件设计的哲学》）** — 从三处寻找理解、使用或修改的实际负担：
  - **变更放大** — 改一条规则，有哪些地方必须跟着改？
  - **认知负担** — 要正确使用或修改它，一个人得同时记住哪些信息？
  - **未知未知** — 哪些依赖、前提或影响范围，使用者在动手前很难发现？

指出造成负担的具体依赖或表述不清之处。即使功能齐全，也要看概念模型能否自洽。即使文件很多，也要根据实际理解和修改成本判断复杂性。

## 用什么证据判断

实现或交付任务，读回产物，按需运行代表用例、测试或查证。学习任务先区分要验证的对象。验证笔记质量，可以对照定义和例子，或沿一道练习找出读者缺少的前提。验证用户是否掌握，则根据 Spec，看用户能否自己解释、预测或尝试。

整体设计有争议、取舍复杂或作者容易受自己思路影响时，可请未参与编写的 subagent 独立检查。给它 Spec、实际产物和具体问题，让它指出证据，主 agent 回查后形成结论。已有测试或 code review 证据仍适用时直接复用。报告结论、依据和仍未验证的部分，检查范围与本次任务相称。

## 发现偏差怎么处理

先定位偏差来自模型、执行还是环境，再判断应由谁处理。用户只要求检查时，报告发现和影响。修正已获授权时，按下列规则处理。

- **缺陷** — 违反已确认的要求。回到产生问题的环节修复，复验受影响的部分。
- **决策偏差** — 实际做法偏离已确认的设计决策。说明原因和影响，由约定的决策者决定接受并更新决策，或恢复原设计。若同时违反 Spec，也标明缺陷。
- **一般设计差异** — 授权范围内的实现细节由 agent 自主处理。有实质影响的差异，留到展示成果时解释选择理由。

如果根因在意图、Spec、模型、方案、Plan 或学习者的理解，就回到相应环节。需要改变已确认的约束或关键设计时，先对齐，再按更新后的基线实施，回查受影响的决策和用例。记录重要问题、处置和复验结果，供 `$show-me` 展示。影响后续工作的决定及时提出。
