# Verify

只说 `$verify` 时，检查最近一轮成果。用户指定对象、问题或范围时，以该约定为准。审查以交付报告结束，保持被检查的产物原样。

## 1. 确定对象和依据

主 Agent 找到实际产物、本轮约定的目标与完成条件，以及仍适用的证据。Spec 可以来自对话、issue 或正式文档。检查代码改动时，明确比较基线，将属于本轮的提交、暂存、未暂存和新增内容纳入范围。检查文档、模型或学习成果时，直接定位相应的材料、例子或练习记录。

## 2. 三个 Agent 并行检查

默认由主 Agent 同时启动三个独立的审查 Agent，各用新的上下文。用户明确只查某个方向时，只派对应的 Agent，按该方向汇总。把同一份审查范围、原始要求和产物位置或内容交给参与审查的 Agent，附上可复用的证据。每个 Agent 只回答分配给自己的问题。

| Agent | 检查方向 | 怎样判断 |
| --- | --- | --- |
| Spec | 实际成果是否满足约定？ | 对照目标、范围、约束和完成条件，用产物、代表用例或已有测试说明满足情况。指出缺失、部分满足、超出约定或行为有误的地方，并引用对应要求。若目标是用户掌握某项能力，依据用户实际解释、预测或尝试的表现。 |
| 概念完整性 | 各部分能否用同一套概念和规则解释？ | 按 Brooks 的概念完整性，沿一个具体场景检查术语、职责、规则和接口是否协调。检查文档时，可对照同一概念的定义、例子和练习，指出哪两处给出了相互冲突的预期。 |
| 复杂性 | 当前结构给理解、使用或修改带来哪些负担？ | 按 Ousterhout 的复杂性，从一次具体使用或变更追踪变更放大、认知负担或未知未知。指出要同步改哪些地方、要同时记住哪些信息，或哪项依赖难以事先发现，并说明实际影响。 |

每个 Agent 返回本方向的结论、发现和依据。每条发现定位到原文、文件位置、具体场景或观察结果，说明影响。未发现问题时简述检查过什么；缺少要求或证据时写明哪项无法判断。

## 3. 汇总报告

主 Agent 收齐本次审查的报告，回查支撑发现的原文或产物，按参与检查的方向并列给出结论。重复的现象可以共用一处证据，保留各方向对其影响的判断。结论看似冲突时，核对它们是否针对同一事实；仍无法判定的分歧连同缺少的证据一起列出。最后简述影响本轮完成判断的问题及未验证事项。
