# Human PR

## 1. 确认范围

读相关 MR、分支提交和工作区改动，用一句话提议「从哪个版本开始、审到哪里、包含什么功能」。等用户确认或调整。已有明确确认时直接沿用。

## 2. 确认分组，逐组提 MR

看完整 diff，把共同实现一个功能或事件、放在一起才容易看懂的改动归为一组。列出建议的阅读顺序，每组用一句话说清要审什么，以及它依赖哪一组。等用户确认或调整。

按确认的分组在审查分支上整理 commit，保留原分支和范围外的工作区改动。每组在 GitLab 提一份 MR，已有对应 MR 时复用。独立组以原目标分支为基准，依赖前一组时以它的分支为基准。核对网页 diff 只展示本组改动，按阅读顺序给出链接。合并由用户按项目流程决定。

## 3. 每份 MR 先走读，再问询

给出当前 MR 的链接，用 [`$walking-through-code`](../walking-through-code/SKILL.md) 陪用户过一遍这份 diff 涉及的业务流程。读完这条业务路线后，用 [`$code-mastery`](../code-mastery/SKILL.md) 围绕同一份改动逐轮提问，由用户给出审查意见。熟悉程度决定展开多深。用户可以随时在网页上对具体代码行写评论。

## 4. 处理评论，交回原 MR 复看

用户说「评论完了，拉一下」时，读取当前 MR 的最新评论和讨论串，结合对应代码处理明确的修改意见。遇到会改变处理方式的歧义，指出是哪条评论、需要用户决定什么。验证改动后推送到原 MR 的源分支；若后续 MR 依赖这次修改，同步受影响的审查分支并核对各组 diff。

给出原 MR 链接，逐条说明评论对应的改动、验证结果和待确认事项。若原先的走读或问询结论有变化，带用户复看受影响的一段。可以在同一份 MR 上重复这个过程。用户说「这份审完了」才进入下一份；全部审完后汇总用户的结论和遗留问题。
