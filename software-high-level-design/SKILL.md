# 建立概要设计

以现状材料、主要业务场景、规则和质量要求为起点。用户可提供需求与业务分析结果或项目的等效材料。先明确是在理解现状、设计变更，还是两者都需要。材料不足时，查证会影响整体方向的信息，并标明仍待确认的假设。

1. **梳理业务职责和候选边界。** 根据场景、关键概念和规则明确业务能力、判断责任与事实归属，说明不同边界之间怎样协作。需要划分领域边界或理清上下文协作时，读取[业务职责与模型边界](references/design.md#业务职责与模型边界)。
2. **建立整体架构。** 结合质量要求和现实约束明确职责、契约、数据归属、部署与协作方式。理解现状时根据材料或实现说明真实结构；提出变更时标明现状与候选设计。处理接口、部署或架构取舍时，读取[整体架构与关键取舍](references/design.md#整体架构与关键取舍)。
3. **推演重要场景。** 用正常流程、关键失败和典型变更说明现有结构的实际行为，或候选方案如何满足需求。设计变更时，按需要比较真实可行的方案，记录代价、设计理由、适用条件和仍需证据支持的风险。

- **理解现状时**，说明实际的职责、数据归属和协作方式，并附上依据。有记录的设计理由引用记录，推断标明依据。
- **提出设计时**，用正常流程和关键失败场景说明方案怎样满足要求，并写清主要取舍。

附待确认的假设和影响方向的未知项。任务已有约定的记录位置时，按[记录与接续](../learn-or-do/preferences.md#记录与接续)同步结果。然后结束本环节。
