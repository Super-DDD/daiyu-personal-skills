# 梳理需求与业务

以业务概况、涉众诉求和目标为起点。用户可提供上一环节的结果，或直接提供足够的业务材料。区分已确认的要求、观察到的行为和待确认的业务问题。

## 用例分析

1. **明确边界与参与者。** 说明当前分析的业务或软件系统，识别与它交互的主要和辅助参与者。主要参与者借助系统达成目标，辅助参与者为过程提供服务。涉众诉求也可能体现为约束。
2. **发现完整目标。** 从业务目标识别能为参与者完成一件有价值的事的用例。先列主要用例轮廓，再细化当前任务相关的场景。把内部操作和 CRUD 步骤放在所属用例里。
3. **梳理场景与结果。** 说明触发条件、前置状态、主要过程、重要替代路径及失败结果。保留用户可观察的结果与必要的补救方式。质量约束或技术失败会改变用户结果时，在对应场景体现。
4. **写出验收条件。** 用「给定前置状态，当请求或动作发生，那么产生某结果」表达关键例子。尚未明确的结果记为待确认问题。

## 领域探索

1. **发现业务事实。** 从代表场景、材料或访谈找出业务上值得关注的事件，以及相关的角色、命令、外部系统和问题。按业务意义判断领域事件，可用过去式表达。
2. **澄清统一语言。** 说明场景中的关键术语、适用上下文和概念关系。检查同词异义，按需记录业务术语与代码标识符的对应。
3. **提炼规则、策略和不变量。** 说明规则的触发条件、适用范围和预期结果，追踪违背规则的业务后果。区分必须维持的业务约束、有效期内应正确执行的策略，以及可替换的实现办法。
4. **理解状态和事实归属。** 明确关键对象的状态、合法变化、判断责任，以及相关事实由谁维护、读取或修改。对外部事实标明权威来源和现有证据。
5. **跨场景检查。** 用其他重要用例、例子或反例检查概念和规则是否一致，补足遗漏，明确术语变化和责任冲突。

将会影响架构、数据、关键流程或发布条件的最低质量要求纳入本轮规格。对照本轮纳入范围的优先目标逐项检查，每个目标都要有代表场景和可观察的验收结果。信息不足时，列出具体待确认的问题。会改变用户结果的规则，用相关的失败场景或反例说明。

交付主要用户目标、代表场景、关键概念与规则、状态和事实归属、质量要求、验收条件与待确认问题。任务已有约定的记录位置时，按[记录与接续](../learn-or-do/preferences.md#记录与接续)同步结果。结束本环节后，用户可将这份材料作为概要设计的输入。
