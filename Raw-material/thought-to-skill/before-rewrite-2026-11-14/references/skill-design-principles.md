# Skill 设计原则

用于设计目标 Skill，也适用于 Thought-to-skill 自身。代码、接口和软件测试相关要求仅用于适用任务。

## 工作过程与思考框架

- **Intent：**该 Skill 的背景、用途与意图；开展具体任务时，理解用户为什么做、希望达成什么。
- **Spec：**指导如何获取、澄清并对齐每次任务的目标、范围、约束、交付预期和验收条件；按需包含已确认的设计要求。
- **Modeling：**围绕目标梳理关键概念、组成与关系，以及动态过程、机制与规则、假设和边界，形成足以解释、推演并指导应用的理解。
- **Work：**完成任务的参考方法，以及如何形成和选择方案、制定 Plan，并开展具体工作。
- **Eval：**依据任务要求与质量标准评估当前认识、过程和成果，根据证据反馈、修正并复验。
- **Review：**复核过程、成果和验证证据，说明结果、理由、与要求的差异及待决定事项，供用户审查。

从与当前目标相关、足够稳定的概念、关系和原理起步，先看整体，再按需要细化或修正。以上方面用于理解与检查，可往返补足，章节按实际工作组织。

制作或改进 Skill 时，先共同想清要完成的事情，随讨论形成 Markdown 梳理稿，保存关键理解、方法、判断依据和适用条件；清楚到足以指导内化即可。已有成熟材料和确认直接沿用，缺口按需要补足。

内化时，将 Intent 提炼到名字与 `description`，说明做什么、何时适用；开头简述目标、通用约束和完成标准；用简短的整体工作模型呈现组成、关系、推进与反馈，再按节点展开具体指导。适合时配简单图示；影响执行判断的意图与要求在正文保留。Eval 与 Review 复用适用的通用指导，特殊任务再补充必要内容。

Skill 沉淀可复用指导。提炼经验时，保留有效做法、关键理由和适用条件；单次背景、偶然顺序与参与方式留在任务上下文。区分本次制作或修改 Skill 的 Spec、目标 Skill 的可复用指导，以及未来运行时获取的具体任务 Spec。

区分制作 Skill 的协作与目标 Skill 的运行。例如，代码学习 Skill 的 Work 描述如何帮助理解代码；整理设想、设计并生成文件属于制作它的工作。制作时的讨论、确认与理解检验不自动成为目标 Skill 对未来使用者的要求。

## 背景与职责

明确用户要完成什么、承担什么职责，以及双方的任务与决策责任；需要时约定 Agent 的职责。已有信息直接沿用，不重复访谈。

先从相关代码、文档和上下文核实任务事实；影响规格或方案选择的知识缺口，在决策前调研。再向用户询问无法可靠获取的信息，如意图、未记录的约定或现状，并说明它会怎样影响判断。资料冲突、过时或无法验证时说明缺口，不把推测当事实。

区分通用知识与本项目、本系统的具体背景，不根据用户身份推测其知识水平。决策前只补充判断所需的事实，用用户熟悉的概念解释；含义不清时先澄清，再提出方案。

## 理解与表达

使用简洁、准确、有指导意义的文字。转述保留关键术语、规则原意和适用条件；直接引用前核对一手材料，解释时用清楚的语言，不自造简称。

介绍概念时先讲问题背景、意图和整体关系，再按需深入。结合图示、例子帮助建立认识，避免开场铺开实现细节。

对新概念、重要约束或难回退的决策，按需请用户用自己的话解释、走一个具体例子或实际尝试，以检查双方是否沟通清楚；不对每条内容固定出题。说不清的记为待确认，不成为已批准的实施与验收基线。已有理解证据直接沿用。

决策困难、说法矛盾或多次交流未解决时，检查是否缺任务背景、解释不清、事实不足或目标冲突，再补充说明或探索，不直接认定用户缺知识。

## 用户决策

先用简短文字说明当前决策共同服务的目标，按编号列出现在能决定的事项；依赖未定事项的留待后续。

每项给出真正可选的方案，说明做法、代价、风险、可能出错的方式与回退难度，再对照目标和后果给出推荐及依据。通常少量选项即可，不固定数量、不凑备选；只有一个合理方案时，说明理由。按相关事项的依赖共同对齐，不固定为每项提问、每项确认。

可回退的决策简要说明、及时确定；难回退或影响重大的决策充分论证。按当前阶段处理已有依据的决策，不必把问题全部留到最终 Review；尚不影响当前工作的事项可记录后续处置时机。关键决策记录必要的事实依据；依据或决策改变时，说明原因并回查受影响的要求、设计和用例。

## 规格与掌握需要

根据当前任务、已有认识和用户意愿，明确本轮需要理解或实际运用哪些内容，以及掌握到什么程度足以支持当前目标。范围可涉及 Intent、Spec、模型、方案与取舍、Plan、实现、Eval 与 Review；详略按需调整，复用已有理解证据，优先补足影响判断的缺口。

分别明确用户的理解需要、关键决策由谁负责，以及 Agent 的自主执行范围。未来使用者需要掌握什么、是否检验其理解，由目标 Skill 的用途与任务要求决定，不因制作时讨论过相关知识就自动加入教学要求。

据当前任务与授权补足必要规格，使 Agent 有依据判断。目标模糊时先交流或小范围探索，形成当前阶段的 Spec，再确认执行范围。

Spec 说明需要满足的要求；模型解释对象怎样运作；方案说明采用什么做法、关键结构与取舍；Plan 安排步骤、依赖和验证。将用户明确要求遵守的设计决策纳入 Spec，其余实现细节留在方案或 Plan 中。实施前按任务规模汇总背景与意图、Spec、方案与 Plan、验证安排和待决定事项，供用户整体 Review；分别核对方案、Plan 的确认状态与实施授权，已有确认和授权直接沿用。可在回复或已有材料中呈现。

## 内容与文字原则

优先说明目标、依据、边界和完成条件。保留能够改善 Agent 判断与行动的内容，补充它缺少的具体背景与方法；通用常识和重复要求按需删减。

常见场景给参考做法和调整条件，并解释影响判断的关键理由。根据任务特点确定约束程度：存在多种合理做法时保留判断空间；顺序、参数或一致性影响正确性时明确要求。只固定确有必要的操作与确认点，避免固化未经验证的提问节奏。

用具体做法、判断条件或必要示例说明要求，避免空泛口号。例子用于解释方法与预期，提炼时保留适用条件。依据试用和反馈补充、改写或删除；同时观察执行过程，检查指令是否造成无效工作。

## 自主执行

按任务需要展开方案、Plan 与实现，共同对齐后自主推进。沿用已确认内容和创建、修改等已有授权，不因进入执行环节重复索要同一授权；未覆盖或实质变化的关键内容再补充对齐。其他细节在授权范围内自主处理。用户未继续介入不自动构成新的授权。

## 评估标准

Eval 按两层标准检查过程与结果，并通过反馈、修正和复验形成闭环：

- **Spec 是否满足：**对照用户已确认的目标、范围、约束、交付预期与验收条件，检查是否服务于 Intent。Agent 应主动识别已有接口契约、兼容性等要求，带入对齐，不只检查用户新写的条目。理解属于目标时，围绕约定的掌握范围，以用户的解释、预测或实际尝试检验，不能用 Agent 的示范代替用户已掌握的证据。
- **质量是否足够好：**分别检查以下两个维度：
  - **概念完整性（Brooks，《人月神话》）：**检查整体是否遵循连贯的设计思想与概念模型，各部分的职责、规则、接口和使用方式是否一致协调，避免局部合理但整体冲突。概念完整性不等于功能齐全。
  - **复杂性（Ousterhout，《软件设计的哲学》）：**检查结构是否增加理解、使用和修改的负担；从变更放大、认知负担、未知未知（不明显的依赖、所需信息或影响范围）识别问题，分析其依赖与不清晰成因。不以代码量、文件数或抽象数量直接判断复杂性。

大阶段结束固定进行 Eval 和 Review。Thought-to-skill 的两个阶段检查点是：共同梳理完成后，检查理解与方法是否清楚、连贯，足以支持内化；Skill 成稿后，检查是否忠实表达共识、符合内容与文字原则，并按约定验证使用效果。目标 Skill 按自身工作阶段安排检查。

阶段内出现偏离 Intent 或 Spec 的主线、同类讨论或尝试反复受阻且没有推进、新事实与关键假设冲突或实际结果明显偏离预期时，触发 Eval。说明差异与证据，区分模型、执行和环境方面的原因，再返回相关部分修正；触发式 Eval 不自动增加完整用户 Review。

先 Eval，修复授权范围内已定位的问题并复验，再提交阶段 Review。复用已有有效检查；按复杂性、偏差与不确定性，必要时请未参与相关工作的独立 Agent 检查，并依据证据判断结论。审查意见不能代替实际产物、试用或运行证据。

按任务规模说明具体问题、影响与必要修正，不据此扩大重构范围。对软件产物使用上述设计标准；对学习和一般文档，借鉴其连贯性与理解、应用负担的判断方法，不替代 Spec 达成或用户掌握知识的证据。

增加少量代码若能使整体更简单、行为更可靠，应说明理由；依赖和抽象本身并非错误，应检查它们是否带来不必要的负担。不为假想需求增加设计。适用时按项目约定检查代码风格与可读性，并按需精简 Spec 本身。

不满足 Spec 是缺陷；偏离已确认设计决策是偏差，二者可能同时成立。发现差异时，依据证据定位原因与影响，回到相关环节修正并复验。授权范围内的修正自主完成；需要改变规格、关键决策或执行范围时，先与用户确认，记录原因并回查受影响的设计、用例和测试。

以本次 Spec、实际产物和必要验证为依据，结论附证据，缺少证据时说明不能确认的部分。重大或暂未解决的问题记录依据、影响、处置与当前状态，按需并入已有材料。参考样本与重复对比按需要扩展，不作为开展 Eval 的前提。

## 测试的必要性

测试优先对应验收条件、接口契约、已知缺陷与有依据的风险。推荐额外测试时，说明验证什么、能发现什么错误及必要性，使用户能理解。

优先复用已有测试，按变更影响和风险选取适当检查。检查测试是否有意义、是否会在行为出错时失败；精简重复、脆弱或维护成本过高的测试，同时保留有效覆盖。不以数量、覆盖率或结构校验代替实际质量判断。

## 审查与结果表达

Review 沿用 Eval 标准，复核阶段成果、实际过程和验证证据，收拢 Spec 达成、概念完整性和复杂性的结论及与要求的差异。有实际产物时读回核实，复用有效检查；尚有关键疑点时按需补充验证。标明版本、范围和证据缺口，区分文档检查与实际效果验证。

按本轮目标与用户的掌握需要展示成果，说明做成了什么、为什么这样做、是否满足 Spec 与意图目标，区分已解决差异、剩余问题与待决定事项。关键认识、改动和取舍按需用图文或案例介绍，提供原文与证据入口。

按任务规模在回复或已有文档中呈现，复用原文与证据。收到反馈后，判断它影响共同理解、Skill 表达还是通用方法，保留适用条件；依据证据补充、修改或删减，复验受影响部分，再交用户审阅。

用户认可当前 Skill 版本后，自动完成最终 Eval 与整体 Review：读回最终产物，回查原始目标、重要修改、验证证据和遗留事项，复用已有有效检查。授权范围内的缺陷修复并复验；关键要求或设计变化再对齐。完成后收束；遇到阻塞或用户决定结束时，报告未解决部分及影响。

## 文件与维护

`SKILL.md` 保留入口、核心指导与关键约束；详细原则、知识、示例按需放入 `references/`，从入口说明何时读取，必要引用使用包内相对路径。有实际需要时再增加脚本或资源；重复且需要确定执行的操作可考虑脚本，并实际运行验证。

必要信息放入 Skill 包内，使其离开原始笔记也能使用。Markdown 梳理稿保存共同理解和设计依据，Skill 保存可复用指导；关键理解变化时回查相关表达。单次样本、运行产物和原始对话保存在任务目录。

保留原始材料和修改前状态。有 Git 时沿用现有仓库和版本序列，以版本号及对应提交记录有实质影响的修改；没有版本管理时先保留副本，按约定建立 Git。版本号用于追溯，不能替代验证证据。边界情况依据实际反馈积累、压缩与修订，避免为单例增加长期负担。
