# Thought-to-skill

先与用户共同想清要完成的事情，再把可复用的理解与方法内化为 Skill，使 Agent 能理解工作、处理关键判断并完成任务。

- **依据当前目标推进：**先查材料与上下文中的事实，只讨论影响判断的缺口；已有认识、确认和授权直接沿用。
- **表达简洁准确：**保留关键术语、原意和适用条件；用简短文字与简单图示解释整体，必要时举例。
- **提炼有用的指导：**保留能改善判断与行动的背景、方法和关键理由；按任务特点规定必要步骤，其余留出调整空间。

产出的 Skill 应忠实表达共识、保留适用条件，使新 Agent 能凭 Skill 和任务输入独立开展工作，并在代表任务中满足 Spec。检查整体是否连贯，以及理解、使用和修改的负担；未验证的部分明确说明。

## 工作模型

主要产物有两种：Markdown 梳理稿保存共同理解与设计依据；Skill 将其中可复用的内容转化为工作指导。关键理解变化时，回查两者受影响的内容。

```text
想法／意图／材料／已完成任务上下文
                  ↓
         共同梳理 → Markdown
                  ↓
         固定 Eval → 用户 Review
                  ↓ 认可梳理成果
              内化为 Skill
                  ↓
         固定 Eval → 用户 Review
                  ↕
              反馈与修正
                  ↓ 认可当前版本
       最终 Eval 与整体 Review → 完成
```

大阶段结束固定进行 Eval 与 Review；阶段内出现偏离主线、反复受阻或依据冲突时，触发 Eval，返回相关位置修正。成熟材料和已确认内容直接沿用，从当前缺口继续；本轮只要求讨论、整理或评估时，完成相应范围。

## 共同梳理事情

阅读相关材料与上下文，先补全背景和 Intent，给出初步理解供用户核对，再逐步展开要求、工作模型和具体方法。想法尚不成熟时，结合例子或必要探索帮助澄清。先核实能够查清的事实，只询问无法可靠获取且影响当前判断的信息。

按需要梳理以下方面，形成足以指导内化的认识：

- **Intent：**为什么做，为谁解决什么问题。
- **Spec：**目标、范围、约束、偏好、预期与验收条件；核实并带入既有要求。
- **Modeling：**关键组成、关系与动态过程，必要时补充机制、规则、假设和边界。从与当前目标相关、足够稳定的认识起步，增量细化或修正。
- **Work：**各节点怎样开展、依据什么判断、有哪些注意事项；方案说明做法与取舍，Plan 安排步骤、依赖与验证。
- **Eval 与 Review：**怎样对照预期检查、分析差异和修正，以及怎样复核、展示成果与证据。

这些方面帮助理解与检查，具体章节按实际工作组织。讨论允许往返；每次推进一组足以判断的内容，沿用已有结论，只对齐新增或发生实质变化的关键内容。

分别明确用户的理解需要、关键决策责任和 Agent 的自主执行范围；补足判断所需背景，按需用解释、预测或尝试检查关键理解。未明确内容标为待确认，不作为已批准要求。需要展开这些方法时，读取 [Skill 设计原则](skill-design-principles.md) 的相应章节。

随讨论更新 Markdown 梳理稿，保存当前共识与重要待定事项。保留原始材料；整理原文时使用副本，已有文档可更新或引用。梳理充分后按下方规则进行阶段 Eval，展示完整认识与差异供用户整体 Review；用户认可后进入内化。

## 内化为 Skill

### 确定表达与实施安排

区分本次制作 Skill 的 Spec、目标 Skill 的可复用指导，以及未来使用时获取的任务 Spec。单次背景与偶然做法留在任务上下文中，提炼方法的条件与依据。

沿用以下表达分工，详略与章节依据目标 Skill 的工作确定：

| 已梳理内容 | 内化后的表达 |
|---|---|
| Intent | `name`、`description` 概括用途与适用场景；影响执行判断的意图在正文保留 |
| Spec | 开头简述目标、通用原则、约束和完成依据；具体任务要求在使用时获取 |
| Modeling | 简短说明整个 Skill 的关键组成、关系、推进与反馈，适合时配图 |
| Work | 按工作节点展开方法、判断条件与注意事项 |
| Eval 与 Review | 复用适用的通用指导，按目标 Skill 的阶段与任务特点安排检查和呈现 |

整体模型帮助看清工作怎样进行，后续指导说明怎样完成。制作时的讨论、确认与理解检验，是否成为目标 Skill 的要求，由其实际用途决定。

编写前，明确采用的内化规则、内容与文字原则，按需参考可用的 `skill-creator` 和官方指导，并遵循 [内容与文字原则](skill-design-principles.md#内容与文字原则)。已有适用原则直接沿用。

主动汇总本次 Spec、目标 Skill 的表达、方案与 Plan、验证安排和待决定事项，供整体 Review，可与梳理阶段 Review 合并呈现。方案说明做法、关键结构与取舍，Plan 安排实施步骤、依赖和验证；实施授权与方案、Plan 的确认分别核对，已有确认和授权直接沿用。需要比较做法时，按 [用户决策](skill-design-principles.md#用户决策) 说明真正可选的方案与推荐依据。

### 编写与调整

按已对齐的方案编写，授权范围内的细节自主处理。合适的已有内容可直接复用、合并和精简。名称与描述简短说明用途和适用条件；正文写清关键方法、条件与理由，常见场景给参考做法，说明何时调整。

将核心指导与必要资源放入自包含的 Skill 文件夹。详细资料按需放入引用文件，并说明何时读取；有实际需要再增加脚本或资源。修改已有 Skill 时，用 Git 保留历史；没有版本管理时先保留副本。

成稿后固定进行 Eval，修正问题再交用户 Review。收到意见时，判断应修正共同理解、Skill 表达还是通用方法，保留适用条件；既补充必要内容，也删除无效指导，复验受影响部分。

## Eval 与反馈修正

### 固定检查与触发条件

| 固定时机 | 检查重点 |
|---|---|
| 共同梳理完成后 | 意图、要求、模型、方法与检查依据是否清楚、连贯，足以支持内化 |
| 内化成稿后 | 是否忠实表达共识，符合内容和文字原则，并按约定验证使用效果 |

先 Eval，修复授权范围内的问题并复验，再进行用户 Review；需用户决定的问题带着依据与建议呈现。目标 Skill 按自身工作阶段安排检查，不直接照搬上述两个阶段。

阶段内遇到以下情况，再进行 Eval：

- **偏离主线：**当前讨论或行动难以说明怎样服务于 Intent 和 Spec。
- **反复受阻：**同类讨论或尝试不断重复，没有新增认识或推进。
- **依据受到挑战：**新事实与关键假设冲突，或实际结果明显偏离预期。

触发式 Eval 说明差异、证据、可能原因和调整安排，不自动增加一轮完整用户 Review。

### 检查依据与修正

依据 [评估标准](skill-design-principles.md#评估标准)，检查 **Spec 达成、概念完整性与复杂性**：过程和成果是否满足已确认要求并服务于 Intent；整体思想、职责和规则是否协调；理解、使用和修改的负担是否合理。

按 Spec、实际风险与已有证据选择必要验证，说明检查什么及其必要性。需要验证运行效果时，观察具体任务中的行为与成果；结构校验和审查意见不能代替实际试用。必要时请未参与编写的独立 Agent 检查。仅在提取样本、重复试用或比较版本时读取 [样本评估与反馈](eval-and-feedback.md)。

根据证据区分模型、执行与环境方面的原因，返回相关理解、方案、指导或资源修正并复验。已授权范围内、不改变已确认要求和关键设计的缺陷自主修复；需要改变这些约定时，再说明影响、建议并对齐。记录重要差异、处置和验证状态，供 Review 使用，复用已有材料。

## Review、迭代与完成

梳理阶段与内化阶段结束时，读回实际产物，复核 Eval 结论，再展示成果、依据、重要差异和待决定事项，供用户整体审阅。主动说明当前进行到哪里、哪些已确定、接下来做什么，沿用已有确认。详细呈现方法按需参照 [审查与结果表达](skill-design-principles.md#审查与结果表达)。

用户提出修改意见后，返回相关位置调整并复验，再交其 Review。用户认可当前 Skill 版本后，自动完成最终 Eval 与整体 Review：读回最终文件，回查原始 Intent 与 Spec、重要修改、验证证据和遗留事项，复用已有有效检查。范围内缺陷修复并复验；关键要求或设计变化再对齐。最终呈现后收束，不重复索要同一认可。

沿用已有版本序列，实质修改形成对应版本号与 Git 记录；仅测试未修改不升版。新 Skill 的首个可试用版本为 **V0**，根据反馈实际修改后为 **V0.1**、**V0.2** 等；主要用途经过充分试用与改进后，由用户决定是否升为 **V1**。版本号不代替验证证据。
