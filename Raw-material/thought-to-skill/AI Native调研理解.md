# 李宏毅那边理解
我的理解就是给 AI 更快地提供一些上下文信息吧。就像之前李宏毅那边理解的：我们通过从认知框架、行为，还有工具上给 LLM 提供一些能力，它才变成了一个 Agent 嘛


其实从 prompt 到 context 到 harness，人类通过一些工具来驾驭模型：

1. 通过人类语言来控制认知框架
2. 通过工具来控制能力边界
3. 通过工作流程来控制行为

一般 Agent 会通过 agent.md 放入 prompt，来控制它的认知框架。

我们可以通过给它一些脚本或cli权限，为它提供更好的环境，让它通过工具来扩大自己的能力边界。我记得 Matt Pocock 的观点也是这样：对工具能力的扩展，提升效果往往是最为明显的。

至于控制行为，一般来说应该有一个整体的标准工作流程：Agent 的行为通常要通过规划、生成、评估这一套整体的标准流程来规范

# 我们来看 OpenAI 的这个最佳实践：

它推荐的最佳使用方式，是不要把它当成一次性助手，而是当成一个队友，随着时间的推移进行配置和改进。

还有一个有用的方法是从正确的任务背景开始，利用 AGENTS.md 提供持久的指导。然后以适合的模式去配备自己的工作流；再下一个就是使用 MCP 接入外部系统，扩展它的能力边界；最后把重复性的工作转化为技能（Skill），实现稳定工作流程的自动化。

其实和上面讲的那些很接近，总结下来我的理解差不多是这样：
• AGENTS.md 给它提供一个认知框架、地图之类的支撑
• MCP 扩展它的能力边界
• Skill 去指导它的行为

在提示词中，一个好的默认做法是包含以下四项内容：目标、上下文、限制条件以及完成条件。这点其实和我的“目标、约束条件 / 验收标准、完成条件”是类似的概念吧


这表示首先要为困难的任务做好一个计划。有几种效果不错的方法：

1. 使用计划模式：在实施前，计划模式允许 Copilot 收集背景信息、提出澄清问题，在实施前制定更完善的计划。
2. 使用 Copilot 进行 interview：也就是说，在实现一个功能前，如果只有一个大概的想法，不确定如何简单描述，可以让 Copilot 先作为一个 interviewer 去挑战你的假设，把模糊的想法转换为具体的概念。
3. 使用 plan.md 的模板：也就是计划执行模板，反正可以让它按照指定的计划去执行嘛。

当某一种提示模式奏效的时候，一些通用的地方可以使用 AGENTS.md。可以将其视为面向 agent 的 README，它会自动加载到上下文中，是代码库中定义 Copilot 工作方式的最佳场所。

一个好的 AGENTS.md 应该包括：
• 仓库布局和重要目录
• 如何运行该项目
• 构建、测试和代码检查命令
• 工程惯例和 PR 预期
• 约束和禁止规则
• 完成工作的含义，以及如何进行验证工作


（其实感觉就是相当于 Intent Spec Modeling eval的这部分，也就是整个项目的work之外的指导内容

具体的每个文件夹及其代码，其实就是它的一个实现、一个 work。


使用 MCP 来了解外部环境。当所需的信息位于代码库之外时，应该使用 MCP。它允许 Cortex 连接到已有的工具和系统去获取信息。

在以下情况下，应该考虑使用 MCP：

1. 所需的上下文信息存在于代码库之外
2. 你需要跨用户或项目的可重复性集成
3. 数据频繁变化

这部分其实相当于拿一个接口去获取更多信息，扩展它的能力和信息边界


将重复工作转化为 SKill：

一旦工作流程变得可重复，考虑把它转换成 SKill 会比较好。每个 SKill 应该限定于一项工作：

1. 列出 2 到 3 个具体的用例
2. 明确定义输入输出
3. 撰写描述，说明该技能的功能和适用场景

我觉得上面那个我暂时可能不太会用，没有更深的感觉，但我确实很认同下面这个：
• 不要试图一开始就考虑所有极端情况，先从一个具有代表性的任务入手，确保它运行良好，然后将该工作流程培养成一项技能，在此基础上不断改进。
• 只有当脚本或额外资源能够提高可靠性（而且是可复用的）时，才应该添加它。

一个很好的经验法则是：如果你不断重复使用相同的提示词，或者纠正相同的过程，那么它很可能就会成为一项技能

使用定时任务处理重复性工作。这个我之前倒是没怎么太使用过，但是看起来也是有一些使用场景的。

一个优秀的候选可能是：总结最近的提交，扫描可能存在的错误，然后按计划运行可重复的分析工作流程之类的。

一个实用的原则是：Skill 决定方法，而 scheduled task 决定进度。如果工作流程需要大量的指导，首先将其转换为一项技能；一旦工作流程变得可预测，安排技能可以 schedule 就可以节省时间。

还有一个提示，是使用 scheduled task 用来做反思和维护，而不只是执行：通过 review 最近的一些聊天、总结以及重复的错误，随着时间推移去提高提示词、指令，或者是 workflow 的内容。


他总结的常见错误：

1. 规则繁琐、堆砌提示，而不是把它们纳入统一的 AGENTS.md 中
2. 不提供如何最佳运行、构建和测试的详细信息，导致 agent 没法执行和验证这些过程
3. 跳过多步繁杂任务的规划
4. 不使用 Git 工作树（git worktree），在同一文件上运行实时任务
5. 在任务可靠之前，就手动安排了重复性任务
6. 把 Codex 当作需要一步一步盯着看的东西，而不是让它与你自己的工作并行使用

# claude最佳实践
开头就说，其实会话中并不需要特别进行某些繁琐操作，它会自动获取一些背景信息之类的。

然后主要介绍了当默认设置不足以满足需求的时候应该怎么做。这种情况通常出现在项目中包含 Claude 仅凭代码无法识别的知识、规则或约束，比如存在于某人脑海中的部署流程、不能读取的文件、任何任务完成之前必须通过的一项检查，以及要控制的预算范围等。

默认情况下程序无法了解项目的具体情况，因此需要进行相应的设置。当有一个 session 没有按照预期进行的时候，几乎总是以下几种情况之一：

1. Claude 构建的东西与你预期的不同，或者每次启动都要重新发现相同的知识，缺少一些无法从代码库中获取的内容：此时你应该告诉它一些上下文，也就是补充它看不到的信息。
2. Claude 说已经完成但实际上没有：通常是因为它没办法检查自己的工作，这时我们应该给它一个检查机制去运行。
3. Claude 做了在这个代码库中不能做的事，或者跳过了一个必须执行的步骤：仅仅靠提示词不能保证这两点，就要强制执行一条不容例外的规则。
4. Claude 的做法是对的，但是花费的时间、权限提示等超出了预期：这时更改一下默认配置即可
   
# 告诉claude它看不到的东西
通常 Claude 每项任务都从阅读你的代码开始。目前的模型在这方面做得很好，它会找到你的文件布局、约定、测试框架及构建方式，通常比你解释得更快。

它找不到的是代码库中不存在的信息，比如：
• 团队在会议上做的决定
• 只存在于某个人脑海中的部署流程
• 集成测试需要的一个环境变量

此时你最好写一个具体的提示。有一个短语比较有帮助，就是 "be ambitious"


然后同样说了，当你还不清楚自己想要什么的时候，不需要在提出要求前把事情全想清楚，不妨让 Claude 先面试你（采访你）。

他推荐的提示词是这样用的：
“我想加一个 API，但我并没有完全想好它。请采访我，直到你可以写出这个 spec，然后把它写成 spec.md”

通常它会创建出一个 spec 文件。此时你如果启动一个新的会话，从中进行构建，就会比较合适


# 保持claude.md简短
因为这个文件 Claude 会加载到每个会话中，意味着它的每一行都会占用 Claude 的注意力（无论它是否相关）。

因此，这个文件最好只包含 Claude 无法从代码本身推断出的信息，效果最佳。比如：

1. 如何验证代码是否正确：具体的测试如何进行
2. 代码中容易存在误导的地方
3. 代码库中未决的决策
4. 你已经修改过的东西

将个人偏好放到 claude.local.md，而不是 claude.md

当工作看起来完成时，Claude 就会停止运行。如果没有其他程序或手段来判断工作是否真正完成，“看起来完成”就是它唯一的判断依据时，实际上意味着你就是测试套件本身：每一个错误都会一直潜伏在那里，直到你发现它。

如果你给它一个有“通过”或“失败”结果的测试用例，Claude 就会自行完成这个循环，进行修改并检查，直到结果正确。

检查的严格程度由您决定，选项包括：
• Claude 自行决定
• Claude 强制执行

但无论你选择哪种方式，都要向 Claude 要证据，比如运行命令的输出，或者是截图


努力程度的话，其实它建议：

如果你想快速来回修改看某个结果，想让它回答得快一点、发散一点，用低 effort 可能会好一点。

如果你想让它谨慎一点，更多地处理一些容易被忽略的边界条件、考虑更多边界情况，可能使用 High 模式会更好一点。Claude 会检查更多的边界情况，并验证更多的工作给出答案，这也是额外的时间和令牌消耗的一个原因


以下这些事情在之前可能比较好，但现在随着 Agent 变得更加智能、上下文窗口变得更长，其实是可以放弃的：

• 积极管理上下文窗口
• 在说明中添加"重要"或强调字母大小写这类内容
• 委托子代理保护上下文
• 强调"更好的能力"或"更仔细想"这种提示词

总的来说，我们应该通过人类语言、工具还有流程，来控制 Agent 的认知框架、能力边界以及行为。

对于我们的代码项目而言：

1. 认知框架：
我们可以通过 AGENTS.md 或 CLAUDE.md 来提供认知部分。主要是提供整个项目通用的一些指导原则、测试要求，以及一些它没办法从代码中获取到的知识。我理解像 intent、spec、modeling、eval 这些部分都可以写到 MD 中。
2. 能力边界：
使用 MCP 去扩展它的能力，也就是扩展它的工具。
3. 行为控制：
可以通过 skill 去控制一些行为。把测试和验证机制说清楚，是非常重要的一件事。


总结下来我的理解差不多是这样：
• AGENTS.md 给它提供一个认知框架、地图之类的支撑
• MCP 扩展它的能力边界
• Skill 去指导它的行为

同时要注意，根目录的 CLAUDE.md 最好保持简短。我们可以使用引用文件的形式，某部分内容让它直接查看引用文件，以此来保持 CLAUDE.md 简短

1. 把验收标准换为完成条件
2. 当我想法比较模糊的时候，一个是想我们一块梳理，再就是采访我，直到我们能形成一个明确的 spec


对于我之前的一个认知架构，我觉得应该做一下转变。

现在类似于类比了软件工程的过程。在我的理解上，软件工程应该是一套很好的方法论或过程，能将我模糊的想法变成系统化的解决方案。再简单点说，它就是一个从需求到方案，或者实现某个意图、完成某项任务的过程。（系统化的方法论或者是思维模式）

整体上或许可以这样对应：软件工程大概是需求分析、概要设计、详细设计，以及测试、部署、维护。那么我当时的整个过程是：

1. Intent to spec：可以理解为需求分析的过程
2. Modeling：概要设计的过程
3. Work 里面的方案、plan 等：详细设计的阶段
4. 实现：具体开始 work、开始工作
5. 接下来的测试维护：其实就是业务的过程
6. Review：专门对人来说，可以插入到某个环节，看做了哪些更改



我想再补充一些之前使用 Agent 修改代码之类的经验：

1. 首先，我不希望有太多的测试。很多时候你会建立过多的测试，必要时对测试进行精简。
2. 代码注释中的内容有时有点太多了。你总是喜欢记录什么时候某个节点修改了什么东西，注释最好不要那么多（虽然这点我不能确定明确是好是坏）。
3. 这里写的文档，我希望它是偏抽象层一些的。接口当然可以很具体，但我不希望你直接引用代码中的某一行或非常具体的细节，比如某一行代码、某个具体数字等。

我希望这套内容稍微稳定一些，变动不要太大。对于代码行、具体数字这些经常频繁变动的细节，之前使用过程中经常会为了它们耗费大量时间精力去处理，但这些其实并不是我关心的地方
