
## 软件生命周期&瀑布模型

```
可以按照软件生命周期，把各部分需要做的工作简要概括如下：
业务理解和确认

1. **业务机会与问题识别**  
    明确要解决什么问题、服务哪些用户、预期产生什么价值，并划定项目的大致范围。
    
2. **可行性分析**  
    从业务、市场、技术、经济、时间与资源等方面判断项目能否实施、是否值得实施，并识别主要风险。市场已有产品、方案、思想。
    
3. **项目立项与计划**  
    确定项目目标、范围、预算、进度、人员分工和交付标准，形成项目计划并获得批准。

----------------------------------------------------------------------------
使用UDD、DDD进行建模工作

1. **需求工程**  
    收集、分析和确认用户需求，将其整理成功能需求和非功能需求，并持续管理需求变更。

2. **系统与软件设计**  
    设计系统架构、模块、数据库、接口和用户交互方式，同时考虑性能、安全性、可靠性和扩展性。

------------------------------------------------------------------------------    
软件开发（实现交给AI）

1. **软件开发**  
    按照设计编写代码，进行代码审查、单元测试、版本控制和构建管理，产出可运行的软件。
    
2. **软件测试与质量保障**  
    通过集成测试、系统测试、性能测试、安全测试和验收测试发现缺陷，确认软件是否满足需求。

-------------------------------------------------------------------------------
部署与维护

1. **交付与部署**  
    准备运行环境，安装或发布系统，迁移数据、配置服务，并制定灰度发布、回滚和应急方案。
    
2. **运行与维护**  
    监控系统状态，处理故障和用户反馈，修复缺陷、优化性能、更新依赖并保障系统稳定运行。
    
3. **软件演进或退役**  
    根据新的业务需求继续扩展或重构系统；当系统不再适用时，进行数据迁移、服务下线和资料归档。
    

此外，还有几项工作贯穿整个生命周期：

- **项目管理**：管理进度、成本、人员、沟通和风险。
- **配置与变更管理**：管理代码、文档、环境、版本和各类变更。
- **安全与合规**：保护系统和数据，满足法律及行业规范。
- **文档与知识管理**：记录需求、设计、接口、测试、运维方法和重要决策。
- **质量管理**：制定质量标准，通过评审、测试和度量持续保证质量。

整体流程可以概括为：

**发现问题 → 判断是否可行 → 制定计划 → 明确需求 → 设计 → 开发 → 测试 → 部署 → 运维 → 演进或退役**
```



—人类在三个方面：认知框架、能力边界、行为 驾驭模型，分别通过人类语言、工具、工作流程实现。人类语言包括prompt、Skills ；工具主要是执行CLI命令；标准工作流程大体上为：规划→生成→评估反馈

Skill 本质上其实还是 prompt，但它可以代表我对某件事的经验或工作流程。我可以给它赋予知识和流程这类内容；类比来看，它包含的就是上下文和行为。

人类通过语言、工具和流程来实现对模型的 harness。工具主要要么是自己的脚本，要么是 agent 自身的能力；而人类的语言和工作流程就应该包含在我的 Skill 中。语言即我给它的认知框架，工作流程即在 Skill 中规定的大致流程（标准工作流程大体上是：规划、生成、反馈）。

回到 Thought to Skill，它的具体定义如下：

Intent：
把我的某个想法、经验、认知框架或流程，转换成一个可复用的 Skill，方便后续开展相关工作。

Spec：

1. 目标：得到一条可复用、符合设计原则且好用的 Skill
2. 约束：遵循我设定的一些 Skill 设计原则，并参考官方的思想与约束
3. 验收标准：得到一条好用、标准且我能理解的 Skill，并且要通过 Eval（对照最开始设立的 Spec 以及设计原则来进行评估）

Modeling 

大概就是几个工作点：

1. 梳理：通盘梳理、理解梳理
2. 内化：
3. 迭代内化完就是一步一步迭代


work：

首先，按照 "learn or do" 这个 Skill 的内容梳理各个节点。通盘考虑 Intent、Spec、Modeling、Work、Eval 和 Review，明确是要复用已有方案还是单独设计特定模块。把这些内容想清楚并梳理出来后，固化到一个 Markdown 文档中，由我来 review 是否符合预期。反复迭代几次、确认差不多之后，再按照我的内化规则进行转化：

1. Intent 转化为 Description 和 Name
2. Spec 转化为最前方的简短介绍（说明目标、约束和验收标准）
3. Modeling 参照现有结构（如果可以的话画个图），简要描述大致工作流程、动静态结构与机制，具体可以参考 "learn or do" 里的详细说明
4. Work 将确定好的流程内化为新 Skill 的具体实现，展开每个节点中详细的指导内容
5. Eval 和 Review 参照我的 Skill 设计原则思想，评估最开始定下的目标是否达成

整个流程结束之后，交付给我进行最终查看。大概就是这样。


Eval：
的话，其实按照我对 Skill 长相和结构的一个偏好来吧。我们刚才内化出来的东西，从上到下基本是这样的：

1. 最上面介绍目标背景，也就是 Spec 的简单介绍。
2. 下面是 Modeling，可以是一个简单的图，或者结构的介绍（也就是结构和流程）。
3. 接下来是具体展开。
4. 最后最好还有一个 Eval 和 Review 的流程。

我觉得在设计原则中：
• 一个是参考我喜欢的这种结构。
• 第二个是我喜欢简洁、准确、具指导性的文字。
• 另外你可以参考一下官方对 Skill 的内容、文字、格式等指导，把它抽出来，或者后面加上引用。这样在 Eval 的时候，也按照这些内容去评估整个过程。
• 还有就是复杂性、概念完整性（其实就是一致性）的检验。

这些 Eval 反馈修正完以后



review：
其实就是为我整个总结汇总一下skill的格式内容，以及一些结论，为我展示、帮助我理解最终的结果


其实整个创建 Skill 的过程，有点像软件工程或者软件生命周期的过程：

首先，我在现实中看到一些行为或想法，觉得可以复用，或者能作为比较好的提示词开头，识别到之后，我就会用刚才那套对它进行建模。

建模之后，让你根据模块细节帮我把它转换成一个可用的 Skill。

至于 Eval Review，算是最初满足基本检验的一步。


这就像软件工程里的业务识别、概要分析、详细分析、实现，最后还有部署和维护。到这一步，虽然 Skill 可以初步使用了，但肯定不是终局，我在实际使用中肯定还会有修改和迭代的意见。

所以此时就需要单独加一个节点。有的时候我调用这个 Skill，可能纯粹只是为了对我之前某一个 Skill 进行迭代。我的理解是加上一个迭代与维护的节点：

1. 版本管理：首先要保证这个 Skill 用上 Git。如果有仓库就用现有仓库；没有的话，就原地初始化一个 Git 环境，至少要保证它有版本迭代的记录。
2. 迭代审查：有的时候我启动它，只是想用这个节点根据我的修改意见（或者工作中参考的一些行为与原则）来进行更新。我会给你一个意见，你通过 Eval 去检查它是否符合我的设计原则、格式要求，以及概念完整性和扩展性，最终给出一个迭代意见并完成迭代。

这样的话，在部署、维护与迭代这块，就能帮到我很多
