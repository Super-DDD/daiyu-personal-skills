# Thought-to-skill 设想

> 本文保留最后一份整合设想。原始设想、历次整理、备份与验证记录保存在 Git 历史中；当前已安装的实现见 [SKILL.md](/Users/daiqinghao/.codex/skills/thought-to-skill/SKILL.md)。

本文区分两类内容：Thought-to-skill 自身的目标与工作过程，以及设计 Skill 时使用的共用原则。Thought-to-skill 也是 Skill，因此这些原则既指导它生成目标 Skill，也适用于它自身。

## 一、Goal：Thought-to-skill 自身的目标与约束

### 背景与意图

我有一些自己的经验、想法或笔记，通常会先按自己的理解整理成一份 Markdown 设想。希望 Agent 与我共同梳理、调研和设计，将其转化成简洁、自包含、可以试用的 V0 Skill，同时让我理解和掌握它的内容。

### 目标与交付预期

保留我的经验和意图，将其提炼为 Agent 能实际使用的指导。最终交付一个独立的 Skill 文件夹；经过必要检查、实际运行、反馈与轻微迭代，并由我人工审核后，定为 V0，拿到其他场景中使用。

### 约束

- 简洁准确，除非有充分理由，不大量扩充；不堆积文件、规则或未经验证的交互细节。
- 由我主导关键取舍，理解方案并确认后再实现。认可方向不等于同意开始实现。
- 原始材料与修改前状态通过 Git 历史保留，当前目录只维护最终文件；后续内容修改先说明方案，按已有授权执行。
- 区分已有经验、个人偏好、未验证设想与 Agent 的建议。借鉴和补充需要说明依据及适用理由。
- 实际效果以运行和使用反馈为依据，说明尚未验证的部分。

## 二、Workflow：共同设计与生成 Skill

以下是默认工作过程。具体采用哪些步骤、在哪些位置确认，应结合已有材料、当前状态和用户期望决定，并向用户说明、确认。

### 1. 接收想法，形成初步设想

阅读用户提供的材料与上下文，捕获想创建的 Skill 的背景、意图、目标、预期和约束。

已有设想 MD 时，直接以它为起点；只有零散想法时，通过交流形成初步设想并记录到 MD。先记录已知内容与未明确的问题，不要求用户开场就全部想清楚。必要时借助概念、例子或小范围探索，帮助用户形成认识。

### 2. 整理格式，获取用户 Review

最初的设想是发散输出，可能零散、重复，夹杂尚未想清楚的问题。先整理格式，是为了让用户看清自己的表达，确认是否符合原意，再讨论内容。

在新文件中整理标题、段落、列表等，此阶段不改写观点或扩充内容。整理后交给用户阅读并给出 Review 意见。

### 3. 根据反馈梳理内容，补足并对齐

收到 Review 意见后，可讨论整篇文档的重组、澄清与改进；说明修改方案，按已有授权执行，通过 Git 保留修改前状态。

共同明确目标 Skill 的用途，以及它的 Goal、Workflow、Eval、Review。材料中已写清的内容直接用于对齐；缺少或不清楚的部分由 Agent 引导补足。

开始设计前，查阅可用的 `skill-creator` 或官方指导，适量参考 OpenAI、Anthropic 和相关、有代表性的公开实践。根据缺口补足必要的领域背景，说明值得借鉴的做法及理由。

双方尽可能全面、具体地对齐。Agent 说明当前理解和尚未明确的问题，并可建议是否继续；是否进入下一步由用户决定。用户明确同意后再推进，未明确的部分也由用户决定是否保留并带入后续工作。

### 4. 判断状态，确认本次流程

根据已对齐的背景、意图和规格，说明当前大概是什么状态、建议经历哪些后续步骤，以及为什么这样安排。经用户确认，确定本次实际采用的流程与确认点。

用户希望深入掌控时，各步骤确认后再执行；希望托管时，在对齐并确认流程后，由 Agent 推进，提供必要的结果与依据。参与深度可以随环节调整。

### 5. 设计方案，经确认后实现

展示目标 Skill 的主体结构、关键内容、文件归属及理由，让用户理解并参与取舍。按共用设计原则组织内容，只有用户明确同意实现后，再创建 Skill 文件夹。

初稿形成后，进入 Eval 与 Review；根据发现的问题回到对应部分修正。

## 三、Eval：检验产物与实际运行

检查生成的 Skill 是否符合用户意图、目标、约束及共用设计原则，完成必要的结构与引用检查，并在实际任务中运行，观察过程与结果。

将实际表现与预期比较，由用户阅读反馈，进行必要的轻微迭代；发现问题后修正、复验。格式或结构检查通过，不等于实际效果已经得到验证。

运行案例、检查标准和反馈方式仍待专门讨论，保持简洁，不提前建立复杂的评估体系。

## 四、Review：审核与 V0 交付

最后的 Review 希望优先由独立 sub-agent 进行，减少自审盲区，并输出审查结果。

向用户清楚展示关键内容、改动及原因、验证结论和未解决部分。用户需要人工过一遍，理解 Skill 在说什么；确认内容与表现符合预期后，交付 V0。后续在其他场景中使用，再根据实际反馈迭代。

这里的 Review 针对产物 Skill 及验证结果；Workflow 中对设想文档的 Review 用于理解和对齐，两者作用不同。

## 五、共用的 Skill 设计原则

以下原则既约束 Thought-to-skill，也用于指导和评价它生成的 Skill。

### 1. 文字表达

使用简洁、准确、具指导意义的文字。在适用范围内提炼可复用规则，保留关键条件和约束。正文以说明性、指导性的分步说明为主；可能产生歧义时，用具体案例或输入输出示例对齐认知。

### 2. 主体框架

采用 Goal、Workflow、Eval、Review 组织核心内容：

- **Goal：**该 Skill 自身的背景、意图、目标、约束和预期。
- **Workflow：**实际如何工作，包括如何获取并对齐每次任务的具体上下文。
- **Eval：**依据什么检验结果，以及如何反馈修正。
- **Review：**如何展示结果、理由和验证依据，供用户理解与审核。

背景、意图和规格说明会共同影响 description 与 Goal 的设计；具体放在哪里以清晰、适用为准，不预先划死界限。这里的“规格”是目标、预期、约束和验收条件等内容的统称。

### 3. 固定指导与任务上下文

实际执行所需的内容，一部分是编写时沉淀的经验、方法与指导，另一部分需要从本次环境、上下文或用户回答中获取。

已写好的流程提供默认指导；每次任务的背景、意图和规格需要理解、对齐。Agent 据此判断并建议本次流程，交由用户确认。发现指导需要补充或修改时，可以进一步讨论。

## 六、文件组织与参考内容

```text
thought-to-skill/
├── SKILL.md
├── references/
├── scripts/       # 有实际需要时增加
└── assets/        # 有实际需要时增加
```

- `SKILL.md`：四个环节及执行时必须掌握的核心原则。
- `references/`：详细设计原则、知识、示例、边界情况和 gotchas；说明何时查阅。
- `scripts/`：可执行的辅助脚本和代码。
- `assets/`：模板及其他资源。

Notice、Knowledge、Guide、Script 等是支持内容的角色，是否拆成文件、如何组织，按实际需要设计，不与四个环节逐项对应。

边界情况逐步积累，并由人 review、压缩和修改；主体原则由人把控，按需要进行简单修改。参考资料与可执行脚本分别承担不同作用。

## 七、后续待讨论的内容

先确认主体职责与内容归属，再细化以下部分：

- **运行评估与反馈：**运行什么任务、怎样判断表现，以及如何反馈和迭代。
- **独立 Review：**审查范围、输出内容，以及与用户人工审核如何配合。
- **输出表达：**保留少量有助于理解的格式指导，不占用太多上下文。参考使用 Matt Pocock `grilling` 的经验，可以考虑分点展示建议、备选方案与简短说明，具体方式后续再确定。

这些待讨论内容暂不预设详细做法，也不直接进入 Skill 实现。
