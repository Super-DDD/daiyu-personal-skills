主要总结两方面的想法：思维模式与文档的组织方式。

一、思维模式与 Skill 的定义

之前在构建 Skill 时陷入了一个误区：先空想出一个可能的方法、方法论或个人理解，然后试图把它直接转化成 Skill。这种做法很有问题。

Skill 应该是从实际流程中抽象出来的沉淀：
• 必须基于充分的实践经验，将跑通的流程沉淀为一份 Skill，这样才是合理的。如果脱离实践经验去空想，总结出来的 Skill 大概率会很差。
• 具体到形式上，Skill 应该是一个从具体流程抽象出来的 Markdown 文档，只包含两部分：Step 和 Reference。

人去理解和总结某件事的底层逻辑，其实很简单的一句话：基于某个目的，进行建模、应用与修正。

二、文档的组织方式

展示时，更加需要注重less is more，每页清晰的一个单词或者是一句话，不超过5句。可能的话一问一答是好的？


写一份用于沟通的文档时，原则是 Less is more，不要堆砌过多内容，只展示最核心想表达的观点。

整体的表达流程可以对应为：Intent -> Spec -> Modeling -> Implement -> Review：

1. Intent & Spec：为了将想法书面化并表达全面，先明确意图并给出 Spec。
2. Modeling：从宏观上进行抽象概括，介绍整体架构。
3. Implement：展开详细介绍。
4. Review：进行整体总结与复盘。

写一份让人容易理解的文档，按照这种自顶向下的表达方式，会更贴合人实际思考和学习的认知过程。

三：稍微浓缩一下刚才看 Matt 和 Potato 的会谈，以及这两天看的视频，凭我的印象总结一下：

Matt 的核心观点：
subgraph 其实是流程化的展示，只包含了 step 以及 reference。他更多是认为人在实现之前要更多参与进去，掌控整个工作的内容，当然检验也是很重要的部分。

Potato 的核心观点：
主要是“信任阶梯”。他现在的工作模式是把自己摘出 agent 的环节、摘出工作流程，让 agent 全自动运转。他的信任阶梯大致是：
• 前期：不信任 agent 的工作内容，需要不断跟进并去理解。
• 后期：随着你为 agent 搭建起一套值得信任的环境（无论是检验方式还是其他约束），最好是在这个约束下它只有一种正确的实现方式。这样你就不需要再去 review 整个过程；即使 review，也只是抽查式检验。

他打了个比方，用厨房来形容：你自己是主厨（chef），副手是 agent，你要思考怎么让厨房流转得更顺畅；甚至说你去教会一个行政主厨，让他代理你让厨房正常运转，你可能只是偶尔去抽检一下。

他更多是把精力放在搭好环境上：搭好那套你认为可以信任 agent 的环境之后，就可以把任务都交给 agent 了。


很多人认为这是一个编程工厂之类的，但他认为这本质上是一个信任问题：你有多信任你的 agent，你的生产力就能迎来多大的爆发。

不是投入盲目信任，而是把工作投入到建设 agent 的环境中

昨天看到 Potato 提到，Agent 倾向于走捷径，用最快的路径把目标完成。

  

Matt 也表达过类似的观点，认为深入阶段需要有独立的目标。他在使用 Plan Mode 中观察到，如果 Agent 知道终点是 Plan，经常随便问几个问题就开始写。

  

这和我实践中遇到的情况一样：当 Agent 知道终点的时候，它会以最快的路径奔向终点，经常随便问几个问题就直接把任务完成了。

  

因此比较好的方式可能是进行拆分、分阶段推进，让每个阶段都有独立的目标。
