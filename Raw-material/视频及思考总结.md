主要总结两方面的想法：思维模式与文档的组织方式。

一、思维模式与 Skill 的定义

之前在构建 Skill 时陷入了一个误区：先空想出一个可能的方法、方法论或个人理解，然后试图把它直接转化成 Skill。这种做法很有问题。

Skill 应该是从实际流程中抽象出来的沉淀：
• 必须基于充分的实践经验，将跑通的流程沉淀为一份 Skill，这样才是合理的。如果脱离实践经验去空想，总结出来的 Skill 大概率会很差。
• 具体到形式上，Skill 应该是一个从具体流程抽象出来的 Markdown 文档，只包含两部分：Step 和 Reference。

人去理解和总结某件事的底层逻辑，其实很简单的一句话：基于某个目的，进行建模、应用与修正。

二、文档的组织方式

展示时，更加需要注重less is more，每页清晰的一个单词或者是一句话，不超过5句。可能的话一问一答是好的？


写一份用于沟通的文档时，原则是 Less is more，不要堆砌过多内容，只展示最核心想表达的观点。

整体的表达流程可以对应为：Intent -> Spec -> Modeling -> Implement -> Review：

1. Intent & Spec：为了将想法书面化并表达全面，先明确意图并给出 Spec。
2. Modeling：从宏观上进行抽象概括，介绍整体架构。
3. Implement：展开详细介绍。
4. Review：进行整体总结与复盘。

写一份让人容易理解的文档，按照这种自顶向下的表达方式，会更贴合人实际思考和学习的认知过程。

```what makes a skill great

Methodology 的核心观点其实就是说，我的 SKill 是流程的一次沉淀吧。具体可看writing-for-agents。



我们在评估或者观察它的话有四个维度：

1. Trigger：触发方式（自动，手动）
2. Structure：内容结构（steps、reference、branch）
3. Steering：引导词（应该使用那种词本身就压缩了很多含义的词）
4. Pruning：剪枝，可能对整个过程没有贡献的内容，应该将它给去掉

四次检查对应四类问题
	触发检查调用时机。
	结构检查每条执行路径读到的材料。
	引导检查代理采取的行动。
	剪枝检查现有文字对行动的实际贡献



Trigger：
触发（由谁去调用它）主要分为两种：

1. Agent 自动调用：
会把一些 description 放入 agent 的上下文，可能减少人的认知负担。但有时可能在非预期的情况下被带入。
2. 手工调用：
有具体需求时再去调用，可以通过一个开关去进行控制。

Matter 倾向于使用手工调用，而不是自动调用，因为这样可以避免带入黑盒的过程。Pocock 愿意承担更多选择工作，以减少模型漏调和时机不确定带来 的评估负担。

Structure：

结构上分成三个部分：step、reference以及branch。

各部分说明：

1. step：说明要做的事以及次序
2. reference：提供定义、模板以及示例，帮助代理去完成步骤
3. branch：每次都用到的材料可以留在主文件；只服务某个分支的材料可以延迟加载

写作时应该先找出必须执行的行动，然后再逐步核对所需的材料。

Steering：
用引导词指向可观察的工作方式：
他表示有的时候想用一段话来表达自己的想法或意图，但往往还是会被曲解。后来发现，如果此时能找到一个 leading word（引导词），它可能就把相关含义全浓缩到一个单词里面了，这是一种很好的方式。
比如他举的例子是 vertical slice（垂直切片），这个词在很多地方都有特指的含义。在Agent工作的时候，如果能从这个词出发开展工作，而且理解它之后、后续的工作含义又能回到这个词，整个过程就会是一个良性循环，工作就会做得非常好。
有时候我们如果能找到一个引导词，去把描述 condense 一下，会是一个很好的方式

让需要深入的阶段有独立目标：
不只是他发现，我也发现，当 Agent 知道目标的话，它在问了几个问题后就会直接朝着目标给出结果。
比如你的目标是一个计划，像 plan mode 的使用经验：当 Agent 直接知道我的目标是生成一个 plan，它随便问几个问题就直接要去生成一个 plan。
这种时候就适合把它抽出来作为一个单独运行的环节，让后续的工作等待我澄清完成以后再启动。
这个方法适合探索明显被赶、被加快的一些环节，比如梳理需求或者是阅读代码库

Pruning：
这里其实是说，他认为 Skill 越短越好，尽可能简短、精确。

当一个 Skill 变得难读以及难以维护的时候，应该先区分它增长的原因，检查三类内容：重复、沉积以及无效指令，它们会有不同的改法：

1. 重复：经常出现在步骤、定义、模板之间。当它们在多个地方重复的时候，更新就容易分叉。应该保留一个权威的位置，其他地方只按需指向它。
2. 沉积：一般来自于长期追加而少有整理。这时候检查一下内容覆盖了哪些分支，如果只有一个分支会用到，就把它迁移到该分支的参考里；过时或与分支无关的内容就可以删除。
3. 无效指令：比如在 Skill 里要求写长而详细的提交说明，删掉这段话，Agent 其实也能写出足够有用的提交说明。这种时候可以先备份一份，然后将某条指令删除，用同一个任务去查看 Agent 的产出。如果发现删除以后没有什么差异，或者没有出现重要的差异，这个指令就可以直接删掉


总之，他建议逐项去验收审查我们的一个 Skill，或者说想要对它进行迭代优化时，可以从这几个维度出发。

他建议从他的仓库中下载那份 writing for edit 的 Skill，用来审查当前自己或别人的 Skill，对这四类内容逐项审查并调整。

比如有一个贯穿四项的例子，就是对于 PRD 流程：

1. 首先明确它适合在需求已澄清、要落成文档时调用。这时我们确定了一个触发时机，应该放在起草之前。
2. 结构上，我们先确定好步骤，对每一点添加必要的材料；必要的话，添加一个分支。实际执行时，如果发现 Agent 总是表现不符合预期，比如走得太快、在关键分支没解决或关键分析没做完的时候就去写文档，就应该让澄清作为一个独立的阶段进行。
3、考虑使用引导词替换一段说明，此外，对于进行过快的，使用单独阶段运行，为其定义好起始条件与结果。
4、至于剪枝（精简），就是按照刚才那三个问题去 review 一下，看有哪些内容可以删除和调整
```

```poteto
守住清晰的边界，把双方确实需要共享的类型或内容放到约定的共享位置，由依赖图和 lint 禁止两个目录相互导入。目录帮助 agent 选位置，检查则在它选错时提供反馈。
```

```matt skills v1.3
其实就是把规格之后的工作，使用了一个新的 skill 去进行组织。

之前我们实现一个任务的前半程，仍然是由 Grill with stock 澄清问题，to spec 形成规格，to ticket 拆出带有依赖关系的工单。这里主要是着重重构了后半程：

1. Implement spec：它组织整份规格的实现，在实现阶段免去逐张派发工单
2. PR：把结果写成便于人工核验的 PR 正文，在审查阶段减少从大片 diff 中推导意图的时间
3. Retro：从已发生的对话中寻找改进仓库和工具的机会，在复盘阶段把成功结果掩盖的摩擦变成下一轮可处理的问题

这三种分别消除了一种具体的负担


一、接下来介绍 implement spec，按任务依赖实现整份规格。

之前有三种派单方式：

1. 最早也是最直观的，是自己运行 implement：做完一张，清理会话上下文，下一张再交给 agent。这相当于让工程师负责整个循环，但依赖工程师会比较麻烦。
2. 写确定性的脚本：让脚本每轮去读取并执行 implement，但这会比较复杂。
3. 使用 implement spec 的主 agent 负责调度工单，工作交给子 agent：这是实现流程自推进（AFK）的一种路径。

工单依赖决定了谁能开工。implement spec 由用户显式调用，它会先阅读规格与工单，找出其中未完成、产出任务的工单，分析它们的依赖关系；没有依赖关系的就并行执行。

调度流程与协作机制如下：
• 调度者建立集成分支，给每张就绪工单分派子 agent 和独立的 worktree。
• 必要时，探索子 agent 会先阅读相关代码或文档，将调查结果放到实现者可访问的位置。
• 每个实现子 agent（subunit）从集成分支起步，调用 TDD 完成工单，然后在交付前合入集成分支并展示进展。
• 工单全部落地后，集成分支会执行整套 code review，由修复子 agent 处理发现的问题，最后清理实现的 worktree。
• 它们以规格、工单、调查笔记和提交作为共享上下文，可以省去在派单消息中重复转述。

关于 PR 与交付（Pocock 表示）：
一份大的规格最终会得到一个大的 PR，常规交付是包含整份规格的集成分支。只有工单系统通过 PR 结项，或者用户明确要求 PR 时，才会在第一次工单合并之后创建草稿（因为分支此时才拥有领先于主分支的提交）。若已有草稿，审查修复后标记为可审查；其他情况下，按工单系统规则结项报告给集成分支。

整个过程中使用 worktree 隔离工作区，但集成仍需要工程判断：独立的 worktree 虽然隔离了各实现者的工作目录，但两个工单仍可能给同一个字段起不同的名字，或者产生冲突，这种问题只有到了合并或整体审查阶段才会显现。

这小节的总结：把验收和阻塞关系写进工单，再让调度器并行执行就绪任务；整份规格最终会落在集成分支上，收尾则依赖整体的审查。


二、然后是 PR 这个skill的一个详细介绍
这里介绍了一下这个 PR：让人快速看懂变更与风险。正文分为三段，分别回答三个问题。

这个 PR 是模型可调用的一个技能，触发场景是撰写 PR 正文时。它规定了正文的结构，让审查者知道改了什么，再看为什么相信它，最后判断把审查时间花在哪。它包含三个部分：

1. Summary（概要）：给出一个能表达核心变化的最小图示
2. Evidence：展示同一行为在变更前后的差异
3. Merge Danger（合并风险）：判断可能性与影响范围

第三个是 glossary.md，
让领域词汇更容易被找到。旧文件是 context.md，来自领域系统设计，后来主要用来保证项目中的术语。后来发现模糊的文件名会让人误解内容，也会让人难以在相关时机判断该读哪份文档。与其使用过于宽泛的命名，现在用 glossary-map.md 指向各领域的专门术语表。

第四个是 Retro，
从真实对话中改进工作环境。Retro 由人显式发起，会复盘 Agent 走过的路径、寻找证据。它默认看当前对话，也可以指定旧对话，通过读取真实记录来追踪 Agent 如何进行搜索、调用、反复询问以及调试，最后把候选的改进按严重程度交给人。

这个技能其实主要检查七类摩擦：
• 代码导航文件和隐含依赖是否好找
• 自动检查是否能稳定捕获失误
• 编码规范
• AGENTS.md 是否承载过多指令
• 工具是否滥用或浪费调用上下文
• 不影响行为的指令是否可以删掉
• 关键日志或信息是否可读

它们会先核对已有脚本和 CI，避免重复推荐仓库中已存在的检查。当时使用时其实暴露了两个不同的问题，其中机械规则适合放进能报错的 lint、git hook 或 CI。
```

```
背景与意图：
我可能刚让 Agent 帮我实现了一大块功能，它进行了很多 commit，并且说自己已经完成了开发和 code review。但最后一步还是需要我去掌握这套代码（至少是生产代码），目前没有更多手段的时候，必须由人来把关。所以需要我充分理解和掌握这份代码，并给出 review 意见。

约束和原则：
```
