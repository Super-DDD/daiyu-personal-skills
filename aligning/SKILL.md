# Aligning

从用户的原话和已有上下文出发，持续访谈，直到双方对齐目标、想法和需求。

按**轮次**推进。围绕当前需要对齐的事项，把前提已明确、可以独立回答的问题放在同一轮，逐题编号并给出推荐答案。等用户回答后，再决定下一轮问什么。

每轮采用以下格式。

```
❓ **Q1** - **<问题标题>**：<问题正文，可分为多段，也可列出多个选项>

➡️ <你的推荐答案>

---

❓ **Q2** - **<问题标题>**：<问题正文，可分为多段，也可列出多个选项>

➡️ <你的推荐答案>
```


每道题都要写成用户只需回答「是」就能采纳推荐答案的形式。当不同选择对结果的影响不直观时，用一个与当前问题相关的例子说明差异。

留意用户回答中出现的新想法、取舍或分歧。如果用户重新界定了问题，就围绕更新后的问题继续追问。若某个问题依赖本轮尚未获得的回答，待用户回答后再提出。

事实由你查明。若本轮某个问题依赖文件系统、工具等环境中的信息，就派一个使用全新 context window 的 sub-agent 核实。查证期间，先问其余可独立回答的问题。待结果返回后，再问依赖该结果的问题。

决策由用户作出。把每项待决事项作为问题交给用户，并等待回答。

用户表示难以理解某个概念、难以作出判断，或反复追问同一点时，先核对双方对关键表述的理解。若用户需要更多背景才能判断，就让 sub-agent 参考 [$modeling](../modeling/SKILL.md)，围绕具体疑问查证并建模。你根据结果向用户解释，再请用户回应。

当没有值得继续追问的问题，影响下一步的假设也都已说清时，根据用户接下来想做的事收尾。

- 如果用户只想理清想法或弄懂一个问题，简要概括双方的理解，请用户确认。有出入就围绕差异继续聊，达成共识后结束访谈。
- 如果接下来要交付具体成果，按 [Grounding 的「确认需求」](../grounding/SKILL.md#1-确认需求)整理本轮讨论，向用户呈现 Background、Intent 和 Spec。用户提出修正时，更新受影响的内容，再请用户核对。用户确认这份完整需求后，直接进入 Grounding 的「确认验收方式」。
