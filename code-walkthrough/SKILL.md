# 代码走读

从用户想弄清的一个问题出发，选一个能在源码里走通的具体场景。已有明确目标或路线时直接沿用。有几条差异明显的路线时，先给出全貌，请用户选一条。图、执行树和源码链接始终对应同一版本。

## 走读一段代码

1. **活动图：发生了什么？** 从业务触发画到可观察的结果，只展开会改变结果的条件。图下用一两句解释这个场景里最值得理解的关系。
2. **类图：谁知道什么，谁负责什么？** 沿用活动图里的角色，换成真实的类名和关键接口，标明谁持有状态、谁作决定、谁接收结果。按函数组织的代码直接画模块和函数。
3. **函数执行树：源码怎么走？** 用缩进文本按实际执行顺序串起调用，从业务入口走到结果。选一两个关键值，在树上标清它从哪来、在哪里写入、后来由谁读取。把决定结果的子调用展开一层，辅助步骤一句带过。保留自然缩进的函数调用树；只在少数停读节点的函数行末尾标 [1]、[2]，函数名仍紧跟树枝。不同调用入口分支列出。树下沿用同一编号和函数名，给出源码链接与要核对的问题，让读者可以从树直接找到对应段落。

三步共用同一个例子。用户想从头走一遍时，连续给出这三步；点名某个函数时，就在原树上展开那个节点。只有线程交错或返回顺序本身难以从树上看清时，再补时序图。

## 走读一份 MR

**先画整份 MR 的改动全貌类图。** 核对源分支相对目标分支的实际 diff。让读者从业务调用方往下扫到数据结构和实现，看到这次涉及哪些类、模块和关键函数，各自做什么，原来的入口或职责去了哪里。串联 MR 按当前这份的目标分支比较。

再从总览图中选一条能解释改动的业务路线，沿活动图和函数执行树读下去。总览类图已经交代清楚的角色可以直接沿用；需要分清该场景的状态归属时，在活动图和执行树之间补一张局部类图。

执行树保留走通业务所需的原有步骤。把审查重点放在树下，挑出真正改动的调用或判断，对照旧版说明参数、触发条件、状态归属或外部结果有什么变化，附当前 MR 版本的源码或 diff 链接。职责迁移和接口改名应说清旧实现的去向，避免给树的每个节点加新旧标签。

读完一条路线后，指出尚未覆盖、最值得看的改动，以及它能回答什么问题。用户选择后继续；用户表示够了，就简短收束已确认的行为和留下的审查意见。
