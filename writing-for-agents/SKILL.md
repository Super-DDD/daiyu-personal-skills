这份参考适用于 Agent 会读到的各类文档，包括 Skill、`AGENTS.md`、`CLAUDE.md`，以及通过引用找到的文档。载体各异，写法相通。文档能让 Agent 的行为更可预期，是因为它每次都遵循同一套过程，具体产出则可以不同。

编写 Skill 时，另读 [Skill 的调用与拆分](SKILL-MECHANICS.md)，了解文件头元数据、调用方式和路由 Skill。

## 上下文指针

**上下文指针（context pointer）** 是 Agent 当前上下文里的一条引用，写明上下文以外有什么材料、什么情况下要去读。Skill 的描述是一种指针，`AGENTS.md` 中指向某份文档的一行文字也是。指针本身的措辞决定 Agent 何时会去读，以及这个行为有多可靠。如果必读资料藏在措辞含糊的指针后面，不同次执行就可能出现偏差。先把指针写清，仍然无效时再把材料移入正文。

指针有两项工作：说明资料是什么，列出哪些**分支**会用到它。分支是文档处理的一种独立情形，不同次执行可能走不同路径。常驻上下文的指针每个词都在每一轮占用空间，比正文更值得精简。

- 把能引导行为的关键词放在前面。它在指针里负责触发读取。
- 每个分支写一个触发条件。几个同义说法如果指向同一情形，就合为一个。
- 正文已经交代的身份信息，可以从指针里删去。

## 两种负担

每新增一份文档或一条指针，都会占用以下两种预算中的一种。

- **上下文负担**由 Agent 承担。`AGENTS.md` 中的一行文字、Skill 描述，以及其他每轮都会加载的内容，无论触发与否，都持续占用 token 和注意力。
- **认知负担**由人承担。人要记住有哪些文档，以及什么时候该找哪一份。人承担了索引的职责，也因此保有主动权。在需要人判断的地方，这份负担值得承担；其余地方可以省去。

通过指针才读到的材料，平时只占指针那一行的上下文。完全没有指针的材料，则全靠人记得去找。

## 信息层级

文档由两类内容构成：**步骤**写 Agent 按顺序做什么，**参考资料**提供按需查阅的定义、规则和事实。一份文档可以全是步骤（操作流程）、全是参考资料（审查规则或本 Skill），也可以兼有两者。安排层级时，要看 Agent 多快就会需要某项内容。

1. **正文中的步骤。** 放在首要位置，写清动作及其顺序。
2. **正文中的参考资料。** 在同一文件内按需查阅。一组平行规则完全可以处于同一层，例如审查时逐项适用的规则。
3. **按需读取的外部资料。** 把内容移到单独文件，用上下文指针写明读取条件。目标可以是同目录的文件，也可以是多份文档都能引用的外部资料。

移出的内容太少，顶层会臃肿；移出太多，又会藏起 Agent 当下需要的指导。**渐进式披露**就是把部分资料沿这个层级下移，让顶层的主次依然清楚。判断时先看分支：所有分支都要用的内容留在正文，只有部分分支用到的资料放到指针后面。步骤一旦埋在大量参考资料中，每次执行能否注意到它们，就会变得不稳定。

同一文件内，相应的做法是**把相关内容放在一起**。层级决定资料放多深，归在一起则决定旁边放什么。把一个概念的定义、规则和注意事项放在同一标题下，让 Agent 读到其中一项时也看到其余几项。重复是同一意思写在多处，分散则是一个意思被拆散在多处。

即使每一行都有用、也没有重复，文档仍可能因为过长而摊薄注意力，每多一行也多一处需要维护。按层级下放参考资料，再按分支或顺序拆分，使每条路径只携带它需要的内容。

## 步骤与完成条件

每个步骤都以一个**完成条件**结束，让 Agent 判断这一步何时做完。条件有两个重要属性。

- **清晰程度。** Agent 能分辨完成和未完成吗？像「已经理解」这样含糊的边界容易让它提前结束。后续步骤已经摆在眼前，会把注意力拉向下一步。先把当前完成条件写清，这是成本最低的局部改动。只有条件确实难以写得更清楚，而且你观察到 Agent 在赶进度时，再考虑拆开步骤，把后面的内容暂时移出视野。要真正做到这一点，需要交接或分派给子 Agent 这样的上下文边界；同一上下文中的调用仍会保留已经看到的步骤。
- **要求的力度。** 「逐一说明每个被修改的模型」比「列出改动」要求更多。条件本身会驱动 Agent 去做必要的调查，无需把每项调查都写成单独步骤。参考文档也可以这样写：「每条规则都已应用」为整份规则集定下了覆盖要求。

有力的完成条件既能检查，也覆盖所有应完成的事项。

## 何时拆分

把一份文档拆成两份，会增加前述两种负担中的一种。只有拆分带来的收益足够时才值得做。

- **按顺序拆分。** 如果看得见的后续步骤让 Agent 草草做完眼前这一步，可以拆开，让它专注于当前需要做的调查。反过来，合并原本分开的步骤会让后续内容提前可见，也可能诱发提前结束。
- **按调用方式拆分。** 这是 Skill 特有的情形，见 [Skill 的调用与拆分](SKILL-MECHANICS.md)。

## 引导词

**引导词（leading word）** 是模型在预训练中已经学到的简短概念，能在执行文档时帮助它思考。例如 *lesson*（一课）、*fog of war*（战争迷雾）和 *tracer bullets*（曳光弹）。反复使用同一个词，含义会在各处的用法中逐渐完整；用很少的 token 就能唤起模型已有的一整套行为。自造词也可以用，但需要清楚定义，还要承担解释成本。优先考虑已有词汇。

引导词有两种作用。在正文里，它引导**执行**，同一个词能唤起相同的行为，在一组平行规则中则能提醒 Agent 留意某类现象。在指针里，它引导**调用**，当提示词、文档和代码库使用同一个词时，Agent 更容易把这些材料联系起来。

留意可以用引导词精简的段落，例如在三处反复列出的三个形容词，或用一整句指针暗示的一个概念。原文给了两个例子：

- 用 *tight*（紧凑的循环）概括「快、确定、开销低」。
- 用 *red*（测试变红）替代「你相信可靠的循环」。遇到这个缺陷时，测试是否变红，是一个可观察的二元结果。

这样既省 token，也给 Agent 一个更准确的思考线索。主动查找能由引导词取代的重复表述。

否定句容易削弱这种引导。说「别想一头大象」时，大象已经进入了注意范围；被禁止的行为同样可能比否定词本身更醒目。正面描述期望行为，例如「注释写成一行」。确实需要用禁令表达硬性边界时，同时给出应当采取的做法。

## 删减

- **每个意思有一个权威出处。** 行为变化时，只需在一处修改。同一意思写在多处，既增加维护和 token 成本，也会让它在信息层级里显得过于重要。引导词有意重复的是词；重复整段含义则会产生上述负担。
- **环境本身也是信息来源。** `package.json` 脚本、配置、目录结构和 `--help` 都可以直接查。文档复述这些内容，相当于维护一份缓存。只有查找代价高时，缓存才值得占据上下文。更值得记录的是难以从环境直接看出的约定、决定背后的原因和配置无法说明的陷阱。读一个文件、跑一条命令就能得到的事实，留在原处就能随环境保持最新。
- **逐行检查相关性。** 这行还影响文档要做的事吗？有些话只是背景铺陈，有些只对个别分支有用，还有些已随着环境或行为变化而过时。短文档更容易维持相关性。只添不删，过时内容就会一层层堆积，最终连仍然有效的指导也很难找出。
- **找出不改变行为的句子。** 模型默认就会做的事，重复指示也要付出上下文成本。判断依据是这个模型在没有这句话时会怎么做。如果两个人对默认行为有分歧，可以实际运行文档来判断。确认一句话不起作用，就整句删掉。引导词也适用同样的检验：如果模型默认就已经相当仔细，*be thorough*（务必仔细）可能没有效果，可以试一个力度更明确的词，如 *relentless*（追查到底）。
