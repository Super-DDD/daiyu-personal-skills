# Skill 设计原则

用于设计目标 Skill，也适用于 Thought-to-skill 自身。代码、接口和软件测试相关要求仅用于适用任务。

## 主体结构与任务上下文

- **Intent：**该 Skill 的背景、用途与意图。
- **Spec：**指导如何获取、澄清并对齐每次任务的目标、范围、约束、交付预期和验收条件；按需包含已确认的设计要求。
- **Work：**完成任务的参考方法，以及如何提出方案、规划并执行。
- **Eval：**依据标准评估过程与结果，反馈、按需修正并复验。
- **Review：**复核成果与证据，清楚表达结果、理由和待决定事项，供用户验收。

五部分用于组织核心内容，不要求五个文件或僵硬串行。Skill 中沉淀可复用指导，具体任务信息从用户、上下文和环境获取。description 概括用途与适用场景，Intent 展开自身定位与要求。

区分制作 Skill 与目标 Skill 的工作。例如，代码学习 Skill 的 Work 描述如何帮助理解代码；整理设想、设计并生成文件属于制作它的工作。

## 背景与职责

明确用户要完成什么、承担什么职责，以及双方的任务与决策责任；需要时约定 Agent 的职责。已有信息直接沿用，不重复访谈。

先从相关代码、文档和上下文核实任务事实；影响规格或方案选择的知识缺口，在决策前调研。再向用户询问无法可靠获取的信息，如意图、未记录的约定或现状，并说明它会怎样影响判断。资料冲突、过时或无法验证时说明缺口，不把推测当事实。

区分通用知识与本项目、本系统的具体背景，不根据用户身份推测其知识水平。决策前只补充判断所需的事实，用用户熟悉的概念解释；含义不清时先澄清，再提出方案。

## 理解与表达

使用简洁、准确、有指导意义的文字。转述保留关键术语、规则原意和适用条件；直接引用前核对一手材料，解释时用清楚的语言，不自造简称。

介绍概念时先讲问题背景、意图和整体关系，再按需深入。结合图示、例子帮助建立认识，避免开场铺开实现细节。

对新概念、重要约束或难回退的决策，按需请用户用自己的话解释、走一个具体例子或实际尝试，以检查双方是否沟通清楚；不对每条内容固定出题。说不清的记为待确认，不成为已批准的实施与验收基线。已有理解证据直接沿用。

决策困难、说法矛盾或多次交流未解决时，检查是否缺任务背景、解释不清、事实不足或目标冲突，再补充说明或探索，不直接认定用户缺知识。

## 用户决策

先用简短文字说明当前决策共同服务的目标，按编号列出现在能决定的事项；依赖未定事项的留待后续。

每项给出真正可选的方案，说明做法、代价、风险、可能出错的方式与回退难度，再对照目标和后果给出推荐及依据。通常少量选项即可，不固定数量、不凑备选；只有一个合理方案时，说明理由并请用户确认。

可回退的决策简要说明、及时确定；难回退或影响重大的决策充分论证。关键决策记录必要的事实依据；依据或决策改变时，说明原因并回查受影响的要求、设计和用例。

## Spec 与关注深度

两种关注深度都可以由 Agent 自主实现，也可以随任务调整：

- **关注结果：**确认目标、范围、约束、交付预期和验收条件，具体实现交给 Agent。
- **关注设计：**在此基础上讨论关键组成、职责边界、接口、数据与控制关系，以及运行过程、状态变化等必要的静态与动态结构。将用户明确要求遵守的设计决策纳入 Spec。

根据关注深度和自主执行范围补足必要规格，使 Agent 有依据判断。目标模糊时先交流或小范围探索，形成当前阶段的 Spec，再确认执行范围。

Spec 说明需要满足的要求，Plan 说明准备如何完成。其余实现细节留在方案或 Plan 中，不自动成为验收约束。按任务规模整理简短开工文档，依 Intent、Spec、Work、Eval、Review 展示，并由用户理解和确认规格与执行安排；已有确认和授权直接沿用。

## 自主执行

优先说明目标、依据、边界和完成条件，提供参考方法，让 Agent 根据上下文推荐具体做法。只对确有必要的顺序、约束和确认点作明确要求，避免固化未经验证的提问节奏或操作细节。

沿用已确认的方案与 Plan 执行，不因进入 Work 重复开工确认；未覆盖或实质变化的关键内容再补充确认。其他细节在授权范围内自主处理。用户未继续介入不自动构成新的授权。

## 评估标准

Eval 按两层标准检查过程与结果，并通过反馈、修正和复验形成闭环：

- **Spec 是否满足：**对照用户已确认的目标、范围、约束、交付预期与验收条件，检查是否服务于 Intent。Agent 应主动识别已有接口契约、兼容性等要求，带入对齐，不只检查用户新写的条目。
- **质量是否足够好：**分别检查以下两个维度：
  - **概念完整性（Brooks，《人月神话》）：**检查整体是否遵循连贯的设计思想与概念模型，各部分的职责、规则、接口和使用方式是否一致协调，避免局部合理但整体冲突。概念完整性不等于功能齐全。
  - **复杂性（Ousterhout，《软件设计的哲学》）：**检查结构是否增加理解、使用和修改的负担；从变更放大、认知负担、未知未知（不明显的依赖、所需信息或影响范围）识别问题，分析其依赖与不清晰成因。不以代码量、文件数或抽象数量直接判断复杂性。

按任务规模说明具体问题、影响与必要修正，不据此扩大重构范围。对软件产物使用上述设计标准；对学习和一般文档，借鉴其连贯性与理解、应用负担的判断方法，不替代 Spec 达成或用户掌握知识的证据。

增加少量代码若能使整体更简单、行为更可靠，应说明理由；依赖和抽象本身并非错误，应检查它们是否带来不必要的负担。不为假想需求增加设计。适用时按项目约定检查代码风格与可读性，并按需精简 Spec 本身。

不满足 Spec 是缺陷；偏离已确认设计决策是需要说明原因、影响并由用户处置的偏差，二者可能同时成立。需要改变规格或关键决策时，与用户确认并记录原因，回查依赖它的设计、用例和测试。

以本次工作的 Spec、实际产物和必要验证为依据，结论附证据，缺少证据时说明不能确认的部分。按问题定位修正相关部分并复验；满足约定要求、遇到阻塞或用户决定结束时收住，报告未解决部分。参考样本与重复对比可按需要扩展，不是开展 Eval 的前提。

## 测试的必要性

测试优先对应验收条件、接口契约、已知缺陷与有依据的风险。推荐额外测试时，说明验证什么、能发现什么错误及必要性，使用户能理解。

优先复用已有测试，按变更影响和风险选取适当检查。检查测试是否有意义、是否会在行为出错时失败；精简重复、脆弱或维护成本过高的测试，同时保留有效覆盖。不以数量、覆盖率或结构校验代替实际质量判断。

## 审查与结果表达

Review 沿用 Eval 标准，直接复核当前成果、实际过程和验证证据，分别给出 Spec 达成、概念完整性和复杂性的结论。可用时优先请未参与编写的独立 Agent 审查，无法独立审查时说明限制。标明版本、范围和证据缺口，区分文档检查与实际效果验证。

面向用户总结做成了什么、为什么这样改、是否满足 Spec 与意图目标，以及关键改动、设计偏差、风险和待确认事项。代码或结构变化按需用图文、案例介绍，提供原文与证据入口，先让用户看清重点，再按需核查。

按任务规模在回复或已有文档中呈现，复用原文与证据，避免重复堆积文件。发现问题时回到反馈修正与复验环节，更新结论，由用户决定是否接受。

## 文件与维护

`SKILL.md` 保留入口、核心指导与关键约束；详细原则、知识、示例按需放入 `references/`，从入口说明何时读取。有实际需要时再增加 `scripts/` 或 `assets/`。Notice、Knowledge、Guide 等是内容角色，不必分别建文件。

必要信息放入 Skill 包内，使其离开原始笔记也能使用。单次样本、运行产物和原始对话保存在任务目录。边界情况根据实际反馈积累，由用户 review、压缩与修订，避免为单例堆补丁；脚本需要实际运行验证。
