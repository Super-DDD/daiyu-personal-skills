# Skill 设计原则

设计与审查产物时使用。这些原则也适用于 Thought-to-skill 自身。

## 文字与范围

使用简洁、准确、具指导意义的文字。在适用范围内提炼可复用方法，保留关键条件和约束，不把个人偏好或未验证设想写成普遍结论。

优先补充会改变 Agent 判断的信息。开放任务说明目的、依据与边界；需要保证特定顺序或结果时再写具体步骤。避免把未经试用的提问节奏、句式或整套问答固化为规则。

文字容易误解时，用少量具体案例或输入输出示例对齐认知。输出以人易于理解为准，不预设复杂格式，也不要求每次列出没有必要的备选方案。

## 四个环节与两个层次

- **Goal：**该 Skill 自身的背景、意图、目标、约束与交付预期。
- **Workflow：**怎样工作，包括如何获取、梳理并对齐每次任务的具体上下文。
- **Eval：**依据标准评估过程与结果，反馈问题，按需修正相关部分并复验，形成闭环。
- **Review：**沿用 Eval 标准复核当前工作，清楚展示结果、理由与证据，供用户理解、核查和决定。

设计 Workflow 时，应描述这个 Skill 执行任务的方法，避免混入本次设计和编写它的过程。例如，代码学习 Skill 的 Workflow 应描述如何阅读代码、建立理解并检验，而整理设想、设计文件结构等属于制作这个 Skill 的工作。

Goal、Workflow、Eval、Review 用于组织 Skill 的核心内容；具体执行顺序在 Workflow 中说明，文件按内容需要划分。

整理设想时，将背景、意图和规格中的相关信息提炼到 description 与 Goal。description 概括用途和适用场景，Goal 展开这个 Skill 自身的目标与要求。两处内容可以关联，不必将原始材料逐句划定归属。规格包括目标、预期、约束和验收条件等。

## 固定指导与任务上下文

Skill 中保留可复用的方法和约束；每次任务的背景、目标和具体要求，则从用户输入、上下文及环境中获取。执行时，将这些信息与 Skill 中的指导结合，选择适合本次任务的做法。

## 用户参与方式

先对齐本次任务的背景、意图、目标、预期和约束，再结合用户表达与交流判断其参与意愿。

- **深入掌握：**用户全程跟进，逐步理解并参与关键判断。先形成当前阶段的目标，再随讨论和反馈完善规格、确认方案后推进。
- **托管：**用户后续介入较少，前期需更充分、具体地确认 Goal 与规格：意图、任务范围、交付预期、约束、验收条件，以及 Agent 可自主判断的范围。简要展示安排，在已有授权范围内自主推进，反馈结果、依据和未解决问题。

前期对齐的充分程度应与托管程度相匹配。目标尚不清楚时，先通过交流或小范围探索形成认识，再确定可托管的范围。影响目标、约束或验收的关键分歧与缺口要先澄清；不影响这些要求的具体方法和执行细节，可由 Agent 判断，无需逐项追问。将严格要求落在目标、约束和验收依据的清晰度上，为选择具体方法保留空间。

参与程度可以随着任务进展调整。用户明确选择托管并认可后续安排，可以构成相应工作的授权；不单凭用户没有继续介入，就认定其已经同意实现。

## 评估标准

Eval 围绕“评估 → 反馈 → 按需修正 → 复验”形成闭环，根据问题返回相关环节改进。

设计目标 Skill 的 Eval，以及评估 Skill 的实际使用效果时，都按以下两层标准检查过程与结果：

- **目标是否达成：**对照 Goal 阶段已与用户对齐的本次任务目标、预期、约束和验收条件，判断是否满足。需要补充或调整判据时，与用户确认。
- **质量是否足够好：**从概念完整性与复杂性分析。概念、术语、规则和各部分关系应一致连贯，避免矛盾或含糊；减少不必要的步骤、规则、文件、依赖和抽象，降低理解、使用和修改的负担。概念完整性不等于功能齐全，复杂性也不只看篇幅或数量。

这两层标准适用于深入掌握与托管两种方式，具体判据随任务细化。结论应附实际证据，缺少证据时说明尚不能确认的部分。参考样本帮助识别差异，不代替已对齐的要求；不同但有效的做法不因偏离参考就判错。

需要修正时，定位到目标与规格、工作流程、配套资源、评估判据或结果展示等相关部分，按已有授权修改；涉及目标或关键取舍变化时，与用户重新对齐。修改后针对问题再次验证，更新结论与依据。满足约定要求就结束；存在阻塞、证据缺口或用户决定暂不修改时，说明尚未解决的问题，不无限循环。

## 审查与结果表达

Review 包括按既定标准复核，以及面向用户整理表达，具体审查内容随任务调整。

- **复核：**沿用 Eval 已确认的标准，直接检查当前产物、实际过程和验证证据，分别给出目标达成、概念完整性和复杂性的结论及依据。可用时优先请未参与编写的独立 Agent 审查；无法独立审查时说明限制。标明审查版本、范围和证据不足的部分，区分文档检查与实际效果验证。
- **表达：**用简洁准确的文字说明最终成果、关键取舍或改动原因、审查发现及待决定的问题。结构、流程或变化难以理解时，可配示意图；提供原文与证据入口，让用户先看清重点，再按需核查细节。

复用已有主报告和证据，避免重复堆积文件。审查发现需修正的问题时，回到反馈修正与复验环节，更新结论；用户据此决定是否接受或继续调整。

## 文件与维护

- `SKILL.md` 保留入口、核心流程与关键约束；description 简洁说明能力和适用场景。
- `references/` 放详细知识、原则、示例和边界情况，并从入口说明何时读取。
- `scripts/` 有实际需要时放可执行脚本；`assets/` 放模板和资源。

Notice、Knowledge、Guide 等是支持内容的角色，不必为每个名称都建立文件。Skill 应能离开原始笔记独立使用；把必要内容放入文件夹，避免依赖作者本地路径或未打包的材料。

边界情况可逐步积累，由人 review、压缩与修订；主体原则由人把控。根据实际失败作小幅修正，避免为单一案例堆补丁。脚本需要实际运行验证，不能只凭存在就认为可用。
