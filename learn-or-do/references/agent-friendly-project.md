# AI-native 项目梳理与内化

围绕新建项目、已有项目整体或指定子模块，形成连贯的软件工程认识与文档，再将知识、接口、工作方法和必要工具组织到项目中，使 Agent 能理解、开展、验证和维护工作。

协作、Spec、执行授权及 Eval／Review 沿用主体 [Learn or Do](../SKILL.md)，工程分析复用[软件工程实践参考](software-engineering.md)。本参考补充如何将认识内化到项目，不要求产品本身具备 AI 功能。

## 适用范围与开始方式

| 对象 | 工作重点 |
| --- | --- |
| 新建项目 | 完整梳理从问题、需求和设计到实现安排、验证、交付与维护的工程过程，形成文档后组织内化；尚未实现的内容标为设计或计划 |
| 已有项目整体 | 从头到尾联系需求、设计、实现、验证和运行维护，形成工程文档；需要重构时补足方案与安排 |
| 指定子模块 | 围绕模块解决的问题梳理目标、职责、接口、实现和验证，同时交代与项目整体的关系 |

先明确本轮对象、目标、交付材料、是否包含实现或重构、执行范围及完成条件。每次按目标选择 Agent 主导或共同学习，也可以在不同部分采用不同参与深度；用户学习深度与项目梳理范围分别约定。已有有效共识、材料和验证直接复用。

梳理对象是项目或模块，用例、流程和场景用于分析、推演与验证。子模块梳理需交代周边依赖，不自动扩大到全项目；系统性梳理与内化也不要求先出现某项 Agent 使用困难。

完成以本轮 Spec 为准：选定范围内的认识与材料连贯，必要指导和能力可找到、可使用，相关验证有据，未解决或未验证内容明确，并满足约定的用户 Review 要求。

## 工作主线与工程偏好

软件工程梳理与文档 → 组织内化 → Eval 与修正 → 用户 Review → 持续维护。

Eval 贯穿各环节，审阅反馈返回相关位置修正，已有成果继续复用。具体实现或重构按本轮安排推进，不要求每轮完整重走所有步骤。

- **测试按需。**优先复用有效检查，围绕关键行为、接口契约、重要风险或实际缺陷选择必要测试。重复、脆弱或只重复实现细节的测试可精简，保留有效覆盖；不按数量判断充分性。
- **注释依信息价值取舍。**保留代码难以表达的理由、约束和陷阱，减少行为复述及“何时改了什么”的流水账，历史由 Git 追溯。默认简洁，仍按理解需要判断。
- **长期文档保持稳定抽象。**主要表达目标、规则、职责、关系、设计理由和接口契约。接口可以具体；避免依赖代码行号、当前测试数量和易变参数取值。实现与配置维护具体细节，临时定位和运行结果按需留在当次记录中。

## 1. 软件工程梳理，形成文档

按软件工程实践参考理解或设计选定对象，先形成问题与价值、需求与领域的整体轮廓，再联系接口、架构与开发方式。在选定范围内保持认识完整，深入程度依据目标和未知调整，不以逐行解释代码为标准。

区分业务要求、实现现状、已确认决策、假设和候选设计。认识应有可核实依据，长期文档优先指向稳定的文档、模块或接口入口。文档与代码矛盾时查证，不直接把当前实现认作业务要求。

### 系统与模块接口

说明系统对外能力、外部交互、主要模块职责及调用契约。接口包含调用者正确使用所需的输入与结果、前置条件、约束、副作用和失败语义；调用顺序、配置或性能条件影响正确使用时再补充。

以深模块作为设计取向：通过简单、清楚的接口封装有价值的行为，减少调用者需要掌握的内部细节，使修改与验证集中在相应职责内。按使用与修改负担判断，不为增加实现复杂度而追求“深”。

区分内部模块协作接口与供 Agent 操作的入口。后者按需选择脚本、CLI、API 或 MCP，说明能力、结果和操作边界，不自动暴露全部内部接口。

### 架构与运行机制

联系静态组成、职责、依赖和数据归属，与动态交互、信息及状态变化、关键失败和恢复。说明整体架构或模块设计如何满足业务目标、质量要求与约束，以及重要取舍的理由。

包含 AI 功能时，在相关模块中说明模型与程序的责任、输入输出、工具边界、失败或降级及效果判断。接口、架构和开发方式是相互联系的关注点，静态、动态等是建模角度，不要求一一对应。

### 开发与协作方式

需求、Spec、设计、实施、验证、Review、交付和维护的通用方法复用 Learn or Do。项目补充特有的协作惯例、决策责任和完成判断，以及环境、依赖、配置、启动、构建和必要检查命令等执行条件；按范围说明发布、排障和恢复方式。

### 形成工程文档

将认识形成项目或模块的工程文档，联系目标、职责、接口、协作和验证。新项目的设计不能作为已验证实现；未取得外部信息或无法实际运行时标明限制。文档可以合并存放，已有材料足够时直接复用；初次内化后，随实现与重构继续更新认识。

## 2. 按职责组织内化

以工程材料为基础，筛选准确且后续需要的内容，考虑重新发现的成本和误解风险。全局共性放项目层，局部知识归所属模块，跨模块关系通过共同入口、架构或接口说明联系；每类事实有明确归属，其他位置引用。

| 内容 | 归属与取舍 |
| --- | --- |
| Agent 工作入口 | 沿用工具识别的 `AGENTS.md`／`CLAUDE.md` 等入口，保留必要指导、命令、限制及详细资料路径，避免多份事实 |
| 领域统一语言 | 沿用词汇表，给出简短定义和需避免的歧义叫法；采用新约定时同步消费规则，不机械改名或按目录拆分 |
| 业务规则与调用契约 | 归业务说明、规格、模块或接口文档；区分应有行为、已实现行为和候选设计 |
| 架构与重要理由 | 静态、动态关系及取舍进入整体或模块设计；有实际取舍、难回退且缺背景难理解的决定按需记录 ADR |
| 开发与运行方式 | 归项目指南、运行手册和必要操作入口，说明前置条件、输入、输出、副作用及失败处理 |
| 验证与操作能力 | 复用检查、脚本、CLI 或其他工具；需要强制落实的约束由程序、权限或相应机制执行 |
| 稳定重复的方法 | 先用已有流程指导；实际有复用价值时提取 Skill，稳定后再考虑自动化 |

通用语言、架构、接口和开发方式可分散组织，但保持整体到模块的阅读路径，不按关注点复制整套材料。词汇表保持为概念定义，操作步骤和实现细节归相应材料。

如包含实现、重构或工具环境改造，按已确认的方案与执行范围推进，并同步必要文档。已有 CLI、API 或脚本足够时直接使用；提示词和工具描述不能单独保证操作边界。

## 3. Eval 与反馈修正

沿用主体对 Spec、概念完整性和复杂性的检查，重点核对：

- **认识与设计：**目标、概念、职责、接口和协作能否联系起来，静态关系与动态行为是否一致，调用者是否需了解过多内部细节，重要结论与取舍是否有依据。
- **内化与使用：**入口和引用是否有效，术语是否一致，关键事实是否重复维护，项目特有工作方式及必要能力能否支持本轮工作和完成判断。
- **维护负担：**测试、注释和文档是否有实际作用，是否重复记录易变细节，新增文件、依赖或步骤是否确有收益。

按变更影响运行必要检查并读回产物，复用未受影响的有效证据。结合实际开发或理解工作，观察 Agent 能否找到知识、使用能力并返回可核对的结果；没有实际使用证据时明确标为待验证，不以材料齐备推断效果已验证。

区分认识、执行和环境原因，按主体 Eval 返回相关位置修正并复验。涉及已确认要求或关键设计改变时重新对齐。产品本身包含 LLM 功能时，其业务效果评估按项目目标开展，分别说明验证状态。

## 4. Review 与交付

展示选定对象的整体认识、主要接口与架构，以及后续 Agent 从哪里开始、怎样开展和检查工作。提供实际文件与工具入口，说明重要变化、取舍、验证结果、维护成本及未解决或未验证事项。

新项目区分设计、计划与已实现成果；已有项目说明改造前后的主要变化。收到反馈后修正相关部分并复验，满足本轮完成条件及约定审阅要求后收束。

## 5. 持续维护

术语、规则、职责、接口、架构关系或工作方式改变时，在同次变更中更新相应材料；命令或工具入口变化时更新使用说明。内部实现调整而契约与设计含义未变时，长期文档可以保持稳定。

根据原因改进：缺知识补对应文档，缺能力补工具或环境，无法判断结果补检查，操作边界需要保证时落实相应限制。清理失效引用、重复指导和无用材料，必要时精简测试和注释，保留有效覆盖和必要解释。真实问题反复出现时再提炼共性指导。

日常维护从受影响部分进入；系统性整理或重构时可重新选择项目或模块。利用 Git 和当次记录追溯变更，环境、依赖或假设变化后复查受影响证据，不机械重跑全部流程。
