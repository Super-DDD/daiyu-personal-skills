# 切片与 issue 记录

用于按切片推进或跨会话接续的软件实现。沿用主体的 Intent、Spec、Modeling、Work、Eval、Review，以及[软件工程实践](software-engineering.md)第 3—7 步，不另建工作阶段。

## 任务与记录的组织

- **父 issue 是整体任务：**承接一个功能、迭代或改造目标，记录整体范围、工程依据、完成条件、子任务关系、进度与下一步。它不是必须实现的一块“父切片”；一个整体任务通常有多个切片，也可以只有一个任务。
- **子 issue 是可执行工作：**通常对应一个可验证的业务切片，也可明确标为迁移、准备或探索任务，说明结果与通过条件。一个切片可跨多个模块；片内改类型、改存储、接入口等通常是实施步骤，不因涉及多个文件就分别建 issue。
- **本地记录：**每个实现 issue 留一篇可理解、可审阅的记录，沿用项目约定位置；未约定时可用 `docs/issues/<编号>-<主题>.md`。本地文件可以直接充当 issue；已有任务系统时引用该记录。正文以 Spec 与 Modeling 为重心，其他过程记录从简。

“用户价值／工作方向”可以比切片粗，不把概要设计中的几条路线直接当作最终粒度。较大的子任务可以继续拆成更小的可执行任务，父任务保留索引与整体完成判断；避免同时维护内容重复的多层父任务。

记录的目标是让用户能说明本片为什么做、要求是什么、怎样运作、为何采用此方案、如何推进、实际做成什么、凭什么判断，以及还缺什么。修改文件列表与测试通过摘要不足以替代这些说明。

共性业务要求、整体架构与决定理由仍由原工程材料维护；本片简短概括相关部分并引用。变更已确认的共性要求或决定时，同步原依据和受影响任务。记录具体改动与执行证据，长期材料保持稳定抽象。

## 切片粒度与开工

先展示候选切片的结果、完成条件及依赖，按主体进行 Eval 与 Review，沿用已有确认。优先贯通一个用户结果所需的层次，做到独立可演示或验证；必要的探索或准备工作也可单独成片，明确通过条件。

除实现能否在一次有限上下文中完成，还要检查用户能否理解并审阅本片：若包含多个独立目标或数套需要分别解释的设计决定，继续拆分。拆后每片仍需有明确结果、边界、验证方式及真实依赖，避免只有“实现存储层”之类无法展示结果的横向任务。行数只作线索，不能代替粒度判断。

横扫调用者的机械变化若确实无法逐片保持可运行，可安排兼容扩展、分批迁移和最后收拢；不能因改动横跨模块就自动套用这一例外。回顾已完成的大批改动时，可以拆成更小的审阅单元，但必须区分“现在按内容划分”与“当时分别实现、提交或验证”；没有中间状态的证据，就不能宣称已经独立交付过。

临近实施时，在本片记录中补齐 Spec、局部模型与方案、Plan 和验证安排，按主体完成开工 Review，沿用已有方案确认与执行授权。不要等编码结束后才首次展示本片结构与取舍；范围内细节仍由 Agent 自主处理。

## 一篇记录应涵盖什么

先写足 Spec 和 Modeling，使读者能从要求看懂本片如何成立、从局部设计看清具体变化。Intent 可用开头一段交代；Plan、实际进展和 Eval／Review 可在末尾简记。六方面不需要同等篇幅，也不强制六个标题或六份文件。

### Spec：展开本片要求

以本片的具体用例为中心，说明谁在什么前提下触发、提供哪些材料，正常结果及重要异常结果是什么，哪些副作用允许或禁止。多个场景可用表格比较，关键场景应能顺着前提、动作和结果读完，不能只列功能名。

列明业务规则、运行／兼容约束、本片边界，以及可逐项检查的完成条件。区分当前验收必须满足的要求与以后才做的目标；用例、约束与完成条件应互相对应。Spec 说明应有什么行为，不从当前代码倒推出业务要求。

### Modeling：解释本片怎样实现与改变

围绕本片，按理解需要联系以下内容，不重抄整体架构：

- **变化前后：**旧行为或职责关系有什么问题，新增、修改、移除和复用了什么；重要变化给出前后对照。
- **静态结构与契约：**具体组成、职责和依赖怎样变化，核心类型或记录表示什么，各调用交换哪些输入／结果、谁拥有事实与副作用。文件清单不能代替这些关系。
- **动态协作：**选取 Spec 中的关键用例，说明实际调用顺序、分支、等待与后台执行、数据或状态变化及失败传播。跨模块的时序应能与静态结构和契约对应；已有业务总览不能代替片内协作。
- **机制与理由：**解释真正使要求成立的办法，如身份与关联、来源选择、状态转换、并发保护、保存与同步边界；说明为何采用、代价与限制。不是每片都需要以上全部机制或固定图示。

已实现内容依据实际代码建立模型；必要时使用类型、函数或字段定位，在当前版本下核实其含义。具体代码入口作为核查线索，正文应能独立解释，不要求用户顺着文件名自己拼出设计。未实现内容则明确是方案，不能描述成已存在的接口。

模型应足以让读者顺着一个用例解释各部分如何协作，预测重要异常的结果，并说明本片相较原来改变了什么。若读完只能说“功能实现了、测试通过”，需返回 Spec／Modeling 补足，而非继续堆验证报告。

### 组织示意

以下结构可合并简短部分；Plan 是 Work 的推进安排，方案归 Modeling，与主体概念一致。

```markdown
# 编号：本片交付结果

父 issue／工程依据；当前状态、相关版本或工作区；真实依赖。

## Intent｜为什么做
本片解决的问题、服务的目标与用户可观察的变化。

## Spec｜要求与边界
具体用例的参与者、前置、触发与材料、正常及重要异常结果；
业务规则、允许／禁止的副作用、约束与范围；对应的完成条件。

## Modeling｜局部模型与方案
改动前后对照；新增／修改／复用的静态组成与调用、数据契约；
关键用例的实际动态协作、状态与失败传播；使要求成立的机制。
联系相应 Spec，说明选择、理由与代价，按需要配结构或时序图。

## Work｜Plan 与实际推进
实施和验证的步骤、依赖与检查点；执行中更新实际进展，
解释影响行为或结构的重要变化，引用相关提交／PR／模块。

## Eval｜评估、反馈与修正
对照 Spec、概念完整性与复杂性，说明检查内容、实际方法与证据；
发现了什么、返回哪里修正、复验结果、未验证部分及其影响。

## Review｜阶段结论与待审事项
本片做成什么、相对方案的重要差异和原因、遗留与下一步；
说明 Agent 的审查结论及用户审阅状态、反馈和后续修正。
```

模型、方案和 Plan 用于指导工作，实际结果用于校正它们。记录维护当前有效认识与重要差异，不抄聊天流水账；不能把实际结果覆盖成“最初就是这样计划”。

为已实现内容补写时，标明“回顾补写”，区分既有规格和计划、从代码核实的现状、本次回顾形成的解释、历史验证与本次补做检查。没有依据的事前决定或执行顺序不编造；补齐文档不能证明当时已经按该流程执行。

## 执行、反馈与跨会话恢复

用户指定 issue 后，由 Agent 读取本片记录、父 issue 与必要依据，核对实际代码、依赖和已有证据，简述当前位置后接续。已有有效认识、决定和授权直接沿用，只补真正影响当前工作的缺口，用户无需重新描述整段历史。

实现中沿途更新实质变化；阶段成果和交付前主动 Eval、修正并复验，再进行 Review。用户可随时要求 Eval 或 Review；即时请求不替代 Agent 原本应做的检查。测试通过之外，还要检查局部与整体设计是否一致，以及本片是否增加不必要的理解、使用或修改负担。

需要临时换会话时，在同一记录留下当前已做／未做、已验证／未验证、未决事项、相关工作区和下一步。满足约定结果、验证及审阅条件后标记完成；仍待用户认可、真实集成或发布时分别记录，不能用笼统“完成”掩盖差别。同步父 issue 的进度与下一步，给出本片文件入口。

## 方法来源与本次调整

[Matt Pocock 的 to-spec](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md) 将已有讨论和决定沉淀为规格；[to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md) 强调可验证的纵向切片、明确依赖，并支持本地一任务一文件，来源为 issue 时可创建子 issue。

这里采用父子任务与切片思想；Matt 的任务模板偏向待交付行为、验收和依赖，本参考进一步展开 Spec／Modeling，以支持用户理解和审阅实际设计。本地长期记录、主动 Eval 反馈循环和父任务进度维护也来自本 Skill 与用户需要。是否写入外部任务系统仍以本轮执行范围为准。
