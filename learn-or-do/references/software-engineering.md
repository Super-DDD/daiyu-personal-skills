# 软件工程实践参考

本参考概括将业务问题逐步转化为可运行、可演进软件的主要方法，也用于梳理已有项目中业务目的、规则、设计与实现之间的关系。

具体目标、范围、理解深度和执行授权沿用主体 `SKILL.md` 的对齐结果，协作及 Eval／Review 也沿用主体。按当前问题选择相关工程工作；各步“结果”说明需获得的认识或产出，可并入现有材料。

## 工程判断原则

- **联系整体与局部：**理解项目整体时，先形成业务目标、参与者、系统边界、主要场景与关键规则的轮廓，再联系设计与实现。局部深入不自动缩小已约定的项目范围。
- **分清要求与现状：**区分业务要求、实现现状、已有决策、假设与候选设计。代码与测试不能单独证明业务应当如此；七步和 DDD 不代表项目真实采用的方法，候选领域边界也不等于现有架构。
- **按证据推进：**需求、领域模型与设计可以往返。影响当前判断的关键未知先补证据或限定范围，其余记录为假设，随探索修正。

## 七步总览

下图表示常见推进关系；具体入口、往返和跳步由本轮任务决定。

```mermaid
flowchart TD
    A["1 明确问题与价值"] --> B["2 梳理需求与业务"]
    B --> C["3 建立概要设计"]
    C --> D["4 选择并细化本轮切片<br/>可验证的用户结果或关键风险"]
    D --> E["5 实现、验证与调整"]
    E --> F["6 交付并观察运行"]
    F --> G["7 复盘并推进下一轮"]
    G -->|下一切片| D
    E -.->|需求或设计反馈| B
    G -.->|目标或边界改变| A
```

### 1. 明确问题与价值

- **思考：**为什么做？为谁做？解决什么问题？如何判断有效？

#### 了解现实业务与获取需求材料

- **了解问题领域：**通过访谈、阅读材料或观察实际工作，整理业务概况、现状与主要问题。
- **分析涉众：**发现相关角色，了解他们的职责、诉求及利益冲突。
- **整理业务目标：**结合涉众诉求明确目标与优先级，以及本轮范围和成功标准。

已有材料直接复用，围绕当前问题补足缺口，再进入用例与领域分析。影响价值或可行性判断的关键未知，应参考现有方案，必要时通过调研或小范围原型补充证据。

- **结果：**业务概况、涉众及其诉求、主要目标与优先级、范围、约束、成功标准、风险与初步计划，足以说明本轮为什么做、为谁做、先解决什么、负责到哪里。

### 2. 梳理需求与业务

- **思考：**参与者要完成什么？业务如何运作？概念之间是什么关系？判断依赖哪些事实，哪些规则必须成立？

以第 1 步获得的业务概况、涉众诉求和目标为起点；支撑材料不足、业务含义不清时先返回补充，再将当前目标细化为用例与领域认识。

#### 用例分析：从参与者目标理解系统行为

1. **明确边界与参与者。**先说明当前分析的是哪套业务或软件系统，再识别在边界外与它交互的角色：主要参与者希望借助系统达成目标，辅助参与者为过程提供服务。涉众的诉求也可能体现为约束，不必都成为独立用例。
2. **发现完整目标。**从业务目标识别主要用例，检查它能否为参与者完成一件有价值的事；内部操作或 CRUD 步骤不自动成为独立用例。先列主要目标的轮廓，再细化与当前任务相关的场景。
3. **梳理场景与结果。**说明触发条件、前置状态、主要过程、重要替代及失败结果。保留用户能观察到的结果和必要的补救方式；实现步骤按后续问题细化。质量约束或技术失败若会改变用户结果，应在适当层次体现。
4. **形成可观察的验收条件。**用“给定前置状态，当请求或动作发生，那么产生某结果”表达关键案例，结果应能明确判断是否满足。结果尚不清楚时记录问题，不当作已批准要求。

#### 领域探索：理解概念、规则与责任

1. **发现业务事实。**结合代表场景、材料或访谈，找出已发生且业务上值得关注的事实，并辨认相关参与者、命令、外部系统和问题点。事件可用过去式表达，但不能只据语法或写库判定；不要直接把执行步骤逐项当成领域事件。
2. **澄清统一语言。**围绕具体场景区分关键名词、动作及事件的含义，注明适用上下文和概念关系。遇到同词异义时检查是否需要区分概念；文档与代码标识符不同可以记录对应关系，不必立即改名。
3. **提炼规则、策略与不变量。**说明触发条件、适用范围和预期结果，追问“不成立会有什么业务后果”。区分必须维持的合法性约束与可替换的实现办法；可变化的策略在生效期间也需要正确执行和验证，不把当前手段固化成业务真理。
4. **理解状态与事实归属。**检查关键对象有哪些状态、哪些变化合法、由谁作判断，所需事实由谁维护、谁读谁写。来自外部系统的事实要标明权威来源及当前证据；相关未知会影响判断时先补证据。
5. **跨场景检查。**用其他主要用例、新例子或反例检查概念与规则是否一致，发现遗漏、含义变化或责任冲突后回修用例和模型。用例不必各自拥有独立事件或领域对象。

- **质量要求：**早期识别影响架构、数据、关键流程或发布条件的最低要求，纳入本轮 Spec；其余改进按风险和价值逐步安排。
- **结果：**主要用户目标及其关系、代表场景、关键概念与规则、状态和事实归属、质量要求、验收条件及待确认问题。能解释当前场景的用户价值，并用正常例子和重要反例说明判断依据，关键歧义已清楚到足以支持下一步时即可继续；不要求补齐全部用例或领域模型。

### 3. 建立概要设计

- **思考：**采用怎样的整体方案与架构满足需求？系统如何分工、协作和部署？关键质量要求如何实现？

概要设计可从业务职责与模型边界展开，再结合质量要求和技术约束形成整体架构。业务边界、架构选择与模块划分相互影响，可以往返调整；局部算法、类或函数等细节随切片展开。

#### 业务职责与模型边界

结合前面的场景、概念和规则，梳理业务能力、判断责任和事实归属，识别候选边界。一个业务流程可能跨多个能力，同一能力也可能服务多个用例，不能直接按流程步骤划分模块。

需要借助 DDD 梳理边界时，可按以下关系推进、往返：

1. **子域与投入重点。**先识别业务问题空间中的能力，按需要区分核心、支撑和通用部分，结合业务价值、专门知识、风险和可用方案分配投入；关键依赖不自动属于核心域。
2. **限界上下文。**识别一套语言和模型保持一致的边界，依据词义、规则、不变量、状态与决策责任判断是否需要分开。子域、限界上下文、代码模块和部署单元不必一一对应；证据不足时保留较粗边界与待确认问题。
3. **上下文协作。**说明交换的命令、事件或查询，谁提供事实，双方如何解释、翻译或共享信息，以及变化由谁承受。按实际关系选择合作方式；存在语义差距时考虑翻译边界，不因对接外部系统就一律增加防腐层。

#### 整体架构与关键取舍

结合主要业务场景、关键规则、质量要求和现实约束，明确影响本轮架构的关键因素。联系系统整体与应用内部，确定主要职责、数据归属、部署及协作方式，区分业务、事务与部署边界。

优先设计深模块，通过简单、明确的接口封装职责内的复杂性，减少调用者需要掌握的知识与操作；必要的行为、失败和一致性契约应清楚。已有且仍适用的架构直接复用，局部细节随切片展开；理解现状时，区分已存在的结构与候选改进。

针对重要选择，用正常流程、失败场景和典型变更比较实际可行的方案，说明如何满足要求及其代价，不要求每轮凑齐备选。关键未知按风险验证，记录决定、待验证假设及重新评估的条件；根据证据调整相关要求和设计。

- **结果：**足以支持本轮工作的概要设计与决策依据，能说明整体架构为何适合目标与约束、各部分如何负责和协作、关键质量要求怎样实现，以及尚待验证的风险。影响整体方向的关键异常提前处理，一般边界与实现细节按切片细化。

需要分片或跨会话推进时，用父 issue 承接本轮整体目标、工程依据、切片关系与进度；具体做法见[切片与 issue 记录](slice-issues.md)。已有规格与设计直接引用。

### 4. 选择并细化本轮切片

- **思考：**本轮最值得交付什么，或最需要验证什么风险？
- **切片与承接：**结合整体目标和代码现状，先给出候选切片的结果、完成条件与真实依赖，检查粒度并供用户 Review；已有拆分直接沿用。每片应能独立验证，并能在有限上下文内讲清和完成；多个独立关注点难以共同审阅时继续拆分。按[切片与 issue 记录](slice-issues.md)建立子 issue、选择当前片，临近实施再补足细节。
- **工作：**围绕一个可验证的用户结果或关键风险限定范围，可跨多个模块，也可针对单个模块做探索实验。沿用已有需求与设计，按当前任务及需要掌握的内容补足本轮细节。
- **场景与局部设计：**推演关键请求触发哪些业务判断与状态变化、产生什么结果、由谁负责，以及重要失败时会怎样。区分应用流程的编排、领域判断与外部交互，再细化必要的接口、数据、一致性要求与技术边界；按需要用结构、时序或状态示意表达。细化接口时，从调用者要完成的任务出发，检查相关复杂性是否在合适边界内消化，并明确输入、结果及必要的失败语义。
- **领域模型：**仅在当前问题需要时采用相关构件：稳定身份与生命周期可用实体表达，按值定义的概念可用值对象表达，必须共同保护的一致性规则可帮助确定聚合边界。业务规则简单时保持模型简单，不要求凑齐战术模式。
- **规格、方案与计划：**将本轮目标、范围、约束和验收条件整理为 Spec，记录解决问题的方案、必要结构与取舍，再安排 Plan 和任务清单。方案说明怎样解决问题及其理由，Plan 说明怎样推进和验证；两者按任务需要细化，理解现状不必产生实施计划。
- **依赖处理：**外部能力尚未实现时，可用接口约定或替身进行局部验证；记录假设、限制、首次真实集成验证的时机与通过条件。暂时无法真实集成时，明确证据缺口与后续安排，不把局部通过视为真实集成已通过。
- **结果：**本轮 Spec、必要设计与 Plan，能够说清“做什么、怎样算完成、哪些假设仍待验证”。

切片记录以 Spec 和 Modeling 为重心：展开本片用例、规则、约束与完成条件，再说明改动前后的职责与契约、实际静态结构、动态协作及关键机制；Plan 与验证结果作相应记录。用户应能看清本片改变了什么、怎样运作，不能只得到任务清单、修改文件名或测试报告。

### 5. 实现、验证与调整

- **思考：**行为是否正确？关键失败情况是否处理？设计是否连贯，理解与修改负担是否合理？
- **工作：**按已确认的要求与设计实现完整的最小链路，边编码边检验，按需持续集成与审查；根据证据修复缺陷、重构，并调整需求或设计。
- **恢复与记录：**从指定子 issue、本片记录、父 issue 和必要依据恢复，核对代码、依赖及验证状态后继续，不因换会话重做已完成的访谈或设计。沿途维护本片方案、Plan、实质变化、Eval 反馈与复验、Review 结论；已有有效方案和授权直接沿用，不能只在结束时补一份结果摘要。
- **验证：**适用时将 Spec 的验收条件转为可执行检查，优先围绕稳定契约验证行为，按变更影响与风险选择必要的单元、集成或端到端检查；结合设计审查评价概念完整性与复杂性，并按项目约定检查代码可读性与风格。优先复用有效测试，必要的额外测试说明验证目标与依据；按需精简重复或脆弱的检查，保留有效覆盖。用新案例和反例检验规则与模型；重要规则涉及多个参与者或时间点时，推演相应的交错场景，不只检查一次调用。检查应能发现相关错误，不要求每项任务都配置全部测试类型。
- **反馈与变更：**根据验证发现的问题，按主体 Eval 原则处理缺陷、设计差异与约束疑问，返回相关需求、设计、计划或实现修正并复验。记录重大问题及处置结果，在阶段 Review 展示，不为使当前实现通过而自行放宽标准。
- **结果：**可运行的切片、相关验证与审查证据、更新后的必要材料；说明验收结论以及剩余问题和影响。

### 6. 交付并观察运行

- **思考：**是否具备发布条件？如何发现故障并恢复？是否产生预期价值？
- **工作：**按变更范围和风险准备环境、配置、数据迁移、发布与回滚安排；完成相关验证，发布后观察日志、指标与用户反馈。采用接口假设或替身的部分，交付结论应清楚说明真实集成的验证状态。
- **结果：**可使用的版本、必要的运行说明、发布与运行证据，或明确尚未满足的交付条件。

### 7. 复盘并推进下一轮

- **思考：**哪些假设被验证或推翻？下一步最值得做什么？
- **工作：**根据证据调整需求、模型、设计和计划，将发现的问题按需补入有效检查与文档。按风险与价值安排剩余功能、质量改进或集成验证，再选择下一切片；目标或边界改变时重新对齐，必要时安排迁移或退役。
- **任务进度：**将本片实际结果与证据、未验证事项及约定审阅状态回写记录，满足本片完成条件后再标记完成；同步父 issue 的进度与下一步。沿用既有子 issue，按真实依赖选择下一片，不把代码已写或已提交视为全部完成。
- **结果：**更新后的理解与下一轮计划，或明确的结束、迁移与下线安排。

贯穿全过程关注风险、质量、安全、版本与必要文档。每轮保留可验证的结果、获得的认识和明确的下一步；按当前验收条件与证据收束。
